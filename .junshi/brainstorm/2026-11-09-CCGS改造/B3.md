# B3 · 全量移植为 dsh skill pack（74 skills 全转）

- 一句话：把 74 个 skill 逐条改写成 dsh 原生 skill（frontmatter 改 `name`+`description`，内联 bash 执行改成 Python 脚本调用），49 个 agent 改成 dsh subagent brief，128 份 docs 原样带进项目。
- 技法：10 倍 / 0.1 倍（技法 9）——把移植量放大到极限，看边界在哪里断。
- 核心假设：流程完整度本身就是产能，只要 74 个环节齐全，单人也能跑出 3A 的稳定性。
- 支撑证据：
  - 若成立，收益是「从立项到发布的完整清单」：`create-epics → create-stories → story-readiness → dev-story → story-done → sprint-plan → gate-check → milestone-review → release-checklist`，一条链不缺环。
  - skill 平均体积不小（最大的 `skill-test` 28.8KB、`design-review` 28.1KB、`team-qa` 26.1KB），确有干货密度。
- 反证信号：
  - **断腿率实测 92%**：68/74 顶部内联 `yaml-helper.sh resolve_config`（bash + Claude Code 变量 `CLAUDE_SKILL_DIR`），25/74 直接调 `.claude/scripts/*`；dsh 的 frontmatter 无 `allowed-tools` 消费方 → 迁移＝每个 skill 重写一遍配置解析与脚本层，74 × 约 1 人时 = **74 人时起，且是纯改造不是游戏开发**。
  - 32/74 正文带 Godot/Unity/Unreal 具体指令，在 Phaser 项目里会产出**错指令**（比没有更糟）。
  - 39/74 提到 `blocked`、但依赖 `hooks/`（18 个 bash hook）真正落地拦截；dsh 侧无对应 hook 机制 → 门变成口号（正是我们账本行 9 记过的老坑）。
  - CCGS 自己的度量：同一个 brief，`standard` 档 30 篇文档 / 58 分钟，两个盲评 + 一次真人试玩把它排**最后**——原文结论「extra 29 documents bought traceability, not a better game」。放大到 74 个 skill 同向加码。
- 成本：**≥74 人时**（不含 docs 阅读与 hooks 重写），且期间不产出一个可玩改动；机会成本＝按当前节奏约 10 天开发量。
- 可逆性：**单向**。一旦 74 个 skill 进仓并写进流程约定，回退要删 74 个目录、清 20+ 处交叉引用，且团队已被流程驯化（心理成本不可逆）。
- 结论：**不成立，封存**。它是「文档产能」的正解、是「游戏质量」的误解；唯一值得保留的是它作为**只读参考库**（已落地 `D:\项目\skill\Claude-Code-Game-Studios`），需要哪一节当场进去读，而不是整包接进流程。
