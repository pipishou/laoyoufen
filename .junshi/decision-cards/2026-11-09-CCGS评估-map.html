决策地图 · 是否采纳 Claude Code Game Studios

2026-11-09 ｜ 老友粉店（Phaser 3.90 + TS + Vite + Vitest）｜ 3 选项 × 5 维 ｜ 数据来源：实测 clone + GitHub API + 本地 grep
根问题：一个把 Claude Code 变成"49 agent / 74 skill 游戏工作室"的模板（MIT，37.3k star，仅支持 Godot/Unity/Unreal），对一个 Phaser + TS 的广西老友粉单机网页游戏，是补品、是负担，还是只有几块砖有用？
成功判据：本项目的"玩家可见缺陷漏检"问题被结构性堵住，且不新增无法维持的流程负担。
门性质：全量移植会引入 .claude/** 与 production/epics/** 目录结构 → 单向门（引入即迁移债）→ 故出本图。

A · 全量移植单向门

覆盖根因最彻底：把 74 skill + 30 导演门 + 18 hook 全部接入，理论上流程无死角。
成本3–5 天改造（逐条改 frontmatter、把 !`bash …` 内联换 python、Agent/AskUserQuestion 换 dsh 对应物）＋ 每次会话技能清单噪声 ＋ 跟版税（上游 CHANGELOG 88.6 KB / UPGRADING 83.5 KB，8 个月 3.7 万 star 高速迭代）。
触发机制靠 rules 的 paths: 域注入 + hook 在 write/commit 时校验。但 paths: 全指向 .cs/.cpp/gdscript，对 .ts 永不命中 → 规则装载成功却一句不生效，表现与"已遵守"完全一致（静默失效）。
可逆性低：产物落 .claude/**、production/epics/**，回退即迁移债。
实测反证仓库自证：同一 brief 四档 rigor，minimal=1 文档/0 min、standard=30 文档/58 min，四者都能跑能测，但两个盲评 + 真人试玩把 standard 版排最后（"extra 29 documents bought traceability, not a better game"）。

B · 选择性直取 4 件双向门 · 推荐

覆盖根因只搬"语言无关的机制"：
D1 眼睛绿（Playwright 四视口截图 + 哈希戳，story 不闭合除非看一眼）
D2 规则直译（gameplay/ui/data/test 四条 → Phaser/TS 版）
D3 观察≠裁决（L0 加 ran 第三态，未跑记 - 不记 0）
D4 rigor 先验（走 minimal+，不补 GDD 全套）
成本约 6 小时（4+1+1+0.2），零新增依赖：Playwright 本就在账本行 3 的批次里。
触发机制D1 挂在"story 闭合"前（人工一次，脚本产图）；D2 写进项目记忆一级（不做成 skill，避免没人读）；D3 进 l0_rules.py 返回值结构，ran=false → to_human（与既有 fail-closed 口径一致）。
可逆性高：D1 只是 tools/qa/observe.mjs 一个脚本 + 证据目录；D2 是文本；D3 是加字段。任一条不满意可单独撤。
实测支撑本项目四条手机端缺陷（hud.css 1160 行 0 条 @media、#stage 硬钉 1024×768、world.ts:655-660 Scale.NONE、main.ts:138 仅 pointerdown）全部通过了三绿——正是 D1 要堵的洞；l0_rules.py:57 只有两态，pool_texts 为空时 R6 静默通过——正是 D3 要堵的洞。

C · 不采用，只记结论

覆盖根因零：手机端零适配继续只靠人眼发现；L0 的"未跑＝通过"漏洞保留。
成本0（本节评估已花 12 分钟）。
触发机制无。缺陷仍由试玩与用户反馈暴露。
可逆性最高：什么都不做当然可逆。
为什么不够账本行 3 已拍板"先做双端骨架 + Playwright 三视口断言"，验收器本来就要写；D1 只是把这套断言升级成"带证据的闭合条件"，增量成本低于重写一次的返工成本。

五维对照（硬数据）

维度A 全量移植B 直取 4 件C 不采用
引擎匹配度0（全库 phaser 仅 1 次，且在 prototyper.md 当"替代原型工具"；test-run.sh 无 node/vitest 分支）100%（4 件均为语言无关机制）不适用
与已装 5 skill 重复度高（74 个里约 30 个有等价物、25 个绑主机发行、19 个是它自身元工具）无重复（机制层，非 skill 层）—
一次性成本3–5 天≈6 小时0
持续成本跟版税 + 清单噪声 + Windows bash/python 不稳≈每次 story 一次截图脚本调用0（但缺陷成本在后）
堵住的真缺口理论上全堵，实际因 paths 错配多数静默失效堵住两条实测缺口（无"看一眼"、无"未跑"态）0
推荐 B，置信 HIGH。判据不是"它好不好"，而是"它的哪一层与我们的引擎和成本纪律对得上"：引擎层零匹配、工具层不可运行、流程层高度重复、知识层与证据层可直取。
不选 A 的一条硬理由：rules 的 paths: 永不命中 .ts 会让"装了"与"没装"在行为上无法区分——这比不装更糟。
不选 C 的一条硬理由：账本行 3 的三视口断言本来就要写，D1 是同一套脚手架的增强，不是新增项目。
