> 2026-11-28 · 主窗（老友粉游戏迁移开发评估）

## 一、一句话结论

**跟开罗的差距已经不是「功能少了什么」——14 项里 13 项达标；真正挡路的是两件更硬的事：**

1. **线上现在是 404，谁都玩不到**（P0，一行 nginx 配置的事，但得先知道）。
2. **能玩到的人也留不住**：97 局真玩家，中位数只玩了 **3 个游戏日**，**没有一局活过第 20 天**（游戏全长的 1/54）。而杀手已经定位到一个具体选项上——**开场那个免费的「街边摊」只有 2 座，48/97 的玩家选了它，选它的 48 局里 0 局活过第 5 天。**

所以接下来的活不该是「再补开罗的某个系统」，而是：**先把门修好 → 再把开局那个陷阱填掉 → 再修「日结单教错人」的归因 bug → 然后才谈中期决策与移动端。**

## 四、GAP B-1（P0）：线上现在是 404

这是本轮最重要的发现，跟「游戏好不好玩」无关，是**门关了**。

| 现象 | 证据 |
| --- | --- |
| `http://8.134.86.249/laoyoufen/` → **301** → `https://8.134.86.249/laoyoufen/` → **404** | 本机 curl 与服务器本地 curl 双向确认 |
| `/laoyou-api/health` 同样 404 | 同上 |
| 根 `/` → 301 → `https://8.134.86.249/x7k2beta/` → **200** | 另一个项目活着 |
| 后台服务**是活的** | `curl http://127.0.0.1:8767/health` → `{"ok":true,"version":"1.0.0","ai":true,"events":83,"playtests":97}`；`systemctl is-active laoyoufen-api` → `active` |
| 站点文件**也在** | `/usr/share/nginx/html/laoyoufen/` 有 `index.html` + `assets/index-BEwYZt6y.js` |

**根因链条（三层，缺一不可）：**

1. `/etc/nginx/conf.d/x7k2-80-redirect.conf`（mtime **2026-11-27 20:51:42**，**别人加的**）里 `server { listen 80; server_name 8-134-86-249.sslip.io; location / { return 301 https://$host$request_uri; } }` —— 只按 Host 匹配、不看路径，把 80 上**所有路径（含 laoyoufen）**都 301 到 https。
2. 443 那台 server（`/etc/nginx/conf.d/x7k2beta-ssl.conf`，mtime 2026-11-26 11:14）只 `include /etc/nginx/default.d/x7k2beta.conf`，注释原文写着「**不 include 整个 default.d**，否则同机 aimicro / laoyoufen 的 location 也会被带到 443 上」，并且 `location = / { return 301 /x7k2beta/; }`、`location / { return 404; }` —— **443 上根本没有 laoyoufen 的 location**。
3. 我们自己的 `/etc/nginx/default.d/laoyoufen.conf`（mtime 2026-11-27 17:06:30）内容完好，`location /laoyoufen/` / assets 长缓存 / `location /laoyou-api/` proxy 都在 —— **但它只在 80 生效，而 80 已经被 301 走了。**

**为什么我们的部署脚本没兜住：** `deploy/remote-install.sh:86-97` 只写 `default.d/laoyoufen.conf` + `nginx -t` + reload，**从不检查 443**；`deploy/deploy-cli.ps1` 最后一步外网 verify 硬编码 `http://$ip/laoyoufen/` 与 `/laoyou-api/health`，事故后这两个断言会失败——**但没人跑部署，所以没人发现。**

**修法（三选一，推荐第 3 个）：**

| 方案 | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| 撤掉劫持 | 把 `x7k2-80-redirect.conf` 的 `location /` 改成 `location = /` 或限定 `location ^~ /x7k2beta` | 一分钟 | 动了别人的项目，他那边可能依赖「全站跳 https」 |
| 443 也挂我们 | 在 `x7k2beta-ssl.conf` 的 server 里加一行 `include /etc/nginx/default.d/laoyoufen.conf;` | 五分钟 | 别人注释里明说不要 include 整个 default.d，只加我们这一条文件是安全的 |
| **（推荐）两条一起** | 我们自己的 `laoyoufen.conf` 里再加一台 `server { listen 443 ssl; ... }`（用现有证书或自签），不碰别人的 server 块 | 十五分钟 | 证书得管；但对别人零侵入 |

修完必须把 `deploy-cli.ps1` 的 verify 改成**同时断言 http 与 https**，并加一条「443 上访问 `/laoyoufen/` 必须 200」，否则下次别人的配置一动，我们又静默 404。

### 5.2 杀手已经定位到「开局那个免费的铺位」

| 首日座位 | 局数 | 中位天数 | 平均天数 | 最长天数 | **≥5 天的比例** |

**48 局选了免费的 2 座档，这 48 局里没有一局活过第 5 天。** 而且这 48 局里只有 9 局中途加过座——加座也没救回来（加座后中位天数仍是 3 天）。

### 5.3 为什么：2 座 = 每天最多 33 碗，且第一天就崩

本地探针（同数值、只换铺位，3 个种子取平均，`spawnScale 6 / serve 1 / eat 1 / patience 1.5 / queue 12`）：

| 铺位 | D1 | D2 | D3 | D4 | D5 | D6 | D7 | 七日流失 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **2 座** | 卖 36 **走 22（38%）** | 卖 36 走 55（61%） | 37/44（54%） | 36/37（51%） | 37/37（50%） | 38/32（46%） | 35/39（52%） | **51%** |
| 4 座 | 卖 64 **走 0（0%）** | 73/60（45%） | 75/76（50%） | 76/89（54%） | 76/95（55%） | 77/107（58%） | 74/111（60%） | 51% |
| 6 座 | 卖 72 **走 0（0%）** | 103/43（30%） | 113/104（48%） | 112/108（49%） | 113/116（51%） | 111/157（58%） | 111/183（62%） | 49% |

两个结论都很硬：

1. **2 座档第一天就丢 38% 客人**，4 座与 6 座第一天是 0%（`game/src/sim/customer.ts:302-307 spawnScaleByDay` 只在第 1 天压 ×0.55，够 4 座吃下，不够 2 座）。
2. **流失率长期都稳在 ~50%，与座位无关**——座位改的是**出碗量**（36 / 76 / 112 碗一天），不是流失率。所以「流失率高」本身不是病，是 `spawnScale 6` 的设计；**真正的病是 2 座档让玩家在第一天就看到「走了 22 位」，然后他以为自己定价错了。**

### 5.4 玩家被教的答案是错的（P0 · 归因串线）

线上 12,429 条流失事件里，**12,389 条（99.7%）的文案都是「看价牌走了」**；Top 5 全是 `<客人>（最便宜 ¥10 超预算 ¥8）` 这类。

**但这不是真的。** 机制在 `game/src/sim/customer.ts`：

- 只有「一款都买不起」这一条分支会写 `flow.lastLostReason`（`:411-417`，`flow.lostPrice += 1` 后写文案）。
- 队满（`:373-378` 只 `flow.lostQueue += 1`）与等不及（`:833 flow.lostWait += 1`）**都不写 reason**。
- 而 `game/src/sim/telemetry.ts:153 lostReason: s.flow.lastLostReason` 与 `:173-175 d.reasons[sample.lostReason] += lostDelta` 是**按「当日 lost 增量」整批记账** ⇒ 队满/等不及的流失被整批贴到「上一次写下的价牌理由」上。

**线上直接验证了这一点：**

> 有流失的天数 **291** 天；其中 `peakWaiting >= 10`（队伍顶到上限）**236** 天；这 **236 天里，`reasons` 里一条非价牌条目都没有（236/236）**。

也就是说：**队伍明明堵死了，日结单却在告诉玩家「学生仔嫌贵走了」。** 玩家于是降价——而 `game/src/sim/customer.ts` 的 `walletFloor(state, raw) = Math.max(raw, cheapestPrice(state))` 已经把客人钱包抬到「至少买得起最便宜那款」，**单款 ¥9–10 时根本不该有价牌流失**。降价一分钱换不来一个客人，但玩家已经学会了错误的一课。

`game/src/sim/bottleneck.ts:309-318` 的 `lossSplitOf` 走 `rep.lostQueue / rep.lostPrice / rep.lostWait` 三个独立计数，**是准的**——错的只有遥测 `reasons` 这一路。而 `game/src/ui/hud.ts:619-634 dayNoteOf` 已经按三者主因分流写对了文案，可惜它读的是日结单的 `lostQueue/lostPrice/lostWait`，玩家看不到「哪天是队列走的」的累计趋势。

**修法（一句话）：** `reason` 不该是一个字符串，该是三条计数。把 telemetry 的 `reasons` 换/加成 `{ lostQueue, lostPrice, lostWait }` 增量，`lastLostReason` 只在 `lostPrice` 分支写。这是**纯诊断改动**，按规矩四种子必须逐位不变。

### 5.5 顺带两条（P1，不挡上线）

- **移动端没有 PWA**：`game/public` 目录不存在，`game/index.html` 里没有 `manifest` / `apple-mobile-web-app-*` / serviceWorker。`game/src/ui/hud.responsive.css:84` 竖屏时只给一句「把手机横过来 · 横屏才看得清灶台」——18 台设备里绝大多数是手机，**打开是浏览器地址栏 + 竖屏被劝退**。
- **单存档槽**：`game/src/ui/panels.ts:1531` 文案「存档只保留这一局」。97 局里有 45 局只玩了 1–2 天，这些玩家回来时看到的是「上次的第 2 天」，回不到更早。

- **BJ′ 先派 Team 子窗取证**：`hud.responsive.css` 四段断点 + 竖屏现状 + 五视口基线，子窗读完只回「改哪几行、改成什么」，主窗照单落地。这样不占主窗上下文。
