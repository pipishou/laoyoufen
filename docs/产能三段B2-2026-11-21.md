# 批次二 · 产能三段（2026-11-21）

## 一、这一批解决什么

开罗的 `storeequip` 表里，设备是**并行口数**：灶 1 / 2 / 4 口，粉篓 4 / 8 筒。本作一直是**百分比乘数**（猛火灶一档 0.85^1，四档 0.52），所以：

- 玩家看到的永远是「出碗 2.0 分/碗」一个数，**看不出卡在哪一环**；
- 钩子推荐设备时只能按 `gain.stove` 一个数算，与 `sim/gear.ts` 的产能判断走两套口径（账本 P117）；
- 设备三件（灶 / 粉篓 / 案台）里，只有灶真的在产能链上，粉篓只省钱、案台只抬总闸，**中间那一段（汤）根本不存在**。

这一批把「一碗粉」拆成三段，按开罗的口数模型重做：

```
炒锅 2.2 分 × 1 口  ┐
汤锅 2.2 分 × 1 口  ├─ 三段并行，合计 6.0 分 = 原来一碗的 SERVE_MINUTES
粉篓 1.6 分 × 1 筒  ┘
```

设备升一档 = 那一段多开一口。合计分钟数下降，出碗变快；最慢那一段决定整碗的节拍。

## 二、数据层（`game/src/data/equipment.ts`）

```ts
export type StationId = "wok" | "pot" | "basket";
export const STAGE_MINUTES = { wok: 2.2, pot: 2.2, basket: 1.6 }; // 合计 = SERVE_MINUTES
export const PARALLEL_BY_TIER = {
  wok: [1, 2, 3, 4, 5],
  pot: [1, 2, 3, 4, 6],
  basket: [1, 2, 3, 5, 7],
}; // 下标是档位 0–4（0 = 还没买）
export const STATION_EQUIP = { wok: "stove", pot: "pot", basket: "strainer" };
export const STATION_NAMES = { wok: "炒锅", pot: "汤锅", basket: "粉篓" };
```

设备从三件变四件，新增**汤锅**（`pot`）。四件价格仍是 `CAPITAL.equipmentYuan = [1500, 3800, 9000, 30000]` 同一张表，没有为了新件另定价 —— 货架上多一件，不是多一条价格线。

三条线各有节奏：灶一口一口加（1→5 口），汤锅靠换大锅（1→6 口），粉篓最便宜加得最猛（1→7 筒）。粉篓的第二效果（料钱 ×0.97^n）保留 —— 它是「篓子多、漏勺顺手」的自然结果。

## 三、算法层（`game/src/sim/equipment.ts`）

| 函数 | 作用 |
| --- | --- |
| `stationCount(state, station)` | 这一段现在开到几口 |
| `stationCountAfter(state, station)` | 升一档之后几口（满档返回当前值） |
| `stageMinutes(state)` | 三段各自的分钟数（已按口数摊开）+ `total` |
| `stationServeFactor(state)` | `total / 6`，**单出口**（HUD 分/碗、打烊单产能、钩子挑件全读它） |
| `slowestStation(state)` | 哪一段最慢、几分钟 |
| `equipServeMultiplier` | 旧名保留，等价 `stationServeFactor` |

`sim/bottleneck.ts` 的 `capacityGain()` 跟着改成按段算：

```ts
const totalAfter = (station) => m.total - STAGE_MINUTES[station] / stationCount(state, station)
                                        + STAGE_MINUTES[station] / stationCountAfter(state, station);
const nextServe = (now.serveNow * totalAfter(station)) / m.total;
```

返回 `{ stove, pot, basket, bench, seat }` 五项。**P117 的两套口径合成一套**：钩子挑件、`gear.nextGear` 的产能判断、面板红标现在都读 `capacityGain`。

`sim/hook.ts`：
- `EQUIP_KIND` 补 `pot: "speed"`，`strainer` 从 `"cost"` 改成 `"speed"`（粉篓本来就是三段之一，只算省钱是旧模型的遗留）；
- `stationOfEquip()` / `stationKeyOf()`：卡在炒锅仍是 `capacity:stove`（探针与副行池按它写过），汤锅是 `capacity:pot`，粉篓是 `capacity:basket`；
- `equipGainOf(id, gain)` 取代原来「只认 stove / bench」的三元表达式。

## 四、界面层

**店铺页 · 设备段**（`game/src/ui/panels.ts`）：

```
设备 · 现在出碗 2.0 分/碗 [最慢：炒锅 2.2 分]
一碗分成三段：炒锅 2.2 分/1 口 · 汤锅 2.2 分/1 口 · 粉篓 1.6 分/1 筒。
哪一段最慢就添哪一段，添别的会被最慢那段吃掉。……

猛火灶   Lv 0/4 [炒锅开到 2 口]   现在 1 口 · 2.2 分｜双环猛火……   ¥1,500
汤锅     Lv 0/4 [汤锅添到 2 口]   现在 1 口 · 2.2 分｜一口锅滚一碗汤……¥1,500
粉篓与汤勺 Lv 0/4 [粉篓添到 2 筒] 现在 1 筒 · 1.6 分｜漏勺大小……    ¥1,500
案台与备料区 Lv 0/4 [日上限 +40 碗] 现在日上限 200 碗｜切配……      ¥1,500
```

每一行都写「现在几口 / 几分钟」—— 原来只有 Lv 与「下一档给什么」，玩家不知道自己现在站在哪。

**HUD**：毛利条的 `title` 挂上三段读数：

```
一碗 1.0 分：炒锅 0.4 · 汤锅 0.4 · 粉篓 0.2｜最慢是炒锅（0.4 分）
```

浮层不加宽（右上角只有 190px），鼠标停一下才展开。

**买成之后的 toast**（`upgradeLine`）也改了：`炒锅第 1 档：开到 2 口` / `汤锅第 1 档：开到 2 口` / `粉篓第 1 档：开到 2 筒` / `案台第 1 档：每天多备 40 碗的料`。原来统一说「出碗更快」，买案台也这么说（F8 修过一轮），现在四件各说各的。

## 六、与开罗逐项

| 开罗 | 本作 | 说明 |
| --- | --- | --- |
| `storeequip` 灶 1/2/4 口 | 炒锅 1→5 口 | 借「并行口数」这个形状 |
| 粉篓 4/8 筒 | 粉篓 1→7 筒 | 同上 |
| 汤没有独立设备 | 汤锅 1→6 口 | 开罗把汤算在「汤种」里，本作老友粉的汤是独立一段（爆香 + 滚汤），拆出来更贴真实灶台 |
| 无「段」概念 | 三段 2.2 / 2.2 / 1.6 分 | 开罗是整碗一个数；本作拆段是为了让玩家知道卡在哪 |

**没借的**：开罗设备价 250 / 800 / 1,500 / 8,000 KCU（道具侧价格，÷100 换不了人民币），仍用本作 `CAPITAL.equipmentYuan`。

## 七、新缺口

- **P163**：三段基准 2.2 / 2.2 / 1.6 分是照「一碗 6 分钟」拍出来的比例，没有现实秒数可参照，也没有「哪一段本该更慢」的依据。
- **P164**：汤锅与炒锅在 0 档完全一样（都是 2.2 分 1 口），新局看不出两者区别，玩家可能以为买错了。
- **P165**：粉篓同时管出碗与料钱（两个出口），面板只写了「现在几筒 · 几分」，没写它还在省钱。
- **P166**：`stageMinutes` 没有「三段之间的等待/传递」这一项，真实灶台上「等汤滚」与「等粉熟」是重叠的，现在的模型是纯串行相加。
