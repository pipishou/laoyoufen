# 主料与份量（P46）：把菜单的第一根轴做出来

> 一句话：**老友粉的菜单是按「什么肉 + 几两」分行的**，所以主料从「在架加料的副产物」升级成 10 个可选的 SKU，
> 份量做出二两/三两，两者都只动料钱与售价、不动口味分——口味仍归配方。

## 1. 开罗怎么给这一轴

| 开罗表/条目 | 原文 | 我们的落点 |
|---|---|---|
| `English.lproj__topping.txt`（44 行） | 每件浇头带 `价格两档 / 成本 / 一串加成数字`，价格区间 700–7,700 KCU、成本 20–120 KCU | 主料 10 种，料钱增量 ¥0–2.4、建议加价 +¥1–4 |
| `English.lproj__topping.txt` 里的 `Thin Roast Pork` / `Stewed Pork` / `Fish Powder` | 既是「加料」也是「这碗是谁的」 | 拆两层：**主料**（这张表）决定是谁的粉；**加料**（`data/sides.ts`）客人自己加、按份收钱 |
| `English.lproj__ramen_name.txt` 轴 2 | 份量形容词 `Mini / Small / Healthy / Micro / Petite / Tiny`（小）→ `Towering / Galactic / Ultra / Titanic / Infinite`（大） | 南宁的说法更直接：**二两 / 三两**，不玩形容词 |
| `English.lproj__help.txt` `▼Customers 1` | 「**Wallet**: Products that exceed a customer's wallet are harder for them to buy」 | 主料贵了，客人愿不愿意买由钱包决定（我们的 `priceTolerance` + 加购 `room`） |

结论：开罗把「主料」和「加料」混在一张浇头表里，是因为它的拉面是「自己拼」；
老友粉是**按 SKU 卖**的（老板，一碗老友牛肉粉，三两），所以这一轴必须单独成表。

## 2. 十种主料（`game/src/data/mains.ts`）

料钱是**相对碎肉的增量**（碎肉的料钱已在 `BASE_COST` 的 4.8 里），建议加价只用来提示玩家，不自动改价。

| id | 名称 | 料钱 | 建议加价 | 满意 | 解锁客流 | 开罗对应 |
|---|---|---|---|---|---|---|
| `pork` | 碎肉（默认） | ¥0 | — | +0 | 0 | Thin Roast Pork |
| `offal` | 猪杂 | +¥1.2 | +¥2 | +2 | 120 | Boiled Eggs（第二档） |
| `beef` | 牛肉 | +¥2.0 | +¥3 | +3 | 300 | Stewed Pork |
| `beefOffal` | 牛杂 | +¥1.8 | +¥3 | +3 | 500 | —（本地新增） |
| `trotter` | 猪脚 | +¥1.6 | +¥3 | +3 | 700 | —（本地新增） |
| `duck` | 烧鸭 | +¥1.7 | +¥3 | +3 | 900 | —（本地新增） |
| `brisket` | 牛腩 | +¥2.4 | +¥4 | +4 | 1200 | Stewed Pork |
| `threeFresh` | 三鲜 | +¥0.9 | +¥2 | +2 | 250 | Mixed |
| `fish` | 鱼片 | +¥1.4 | +¥3 | +2 | 1500 | Fish Powder |
| `veg` | 素粉 | **−¥0.8** | −¥1 | +0 | 0 | Corn / Wakame |

现实对照：老友猪杂粉 10 元、老友牛肉粉 12 元、牛腩粉 13–15 元（2025 年南宁），
所以牛肉比碎肉的建议加价就是 +¥3、牛腩 +¥4 —— 一碗的肉成本差 1.5–2.5 元。

## 3. 份量：二两 / 三两（`PORTIONS`）

| 份量 | 成本 | 卖价 | 满意 | 出碗 |
|---|---|---|---|---|
| 二两（默认） | ¥0 | 菜单价 | +0 | ×1.0 |
| 三两 | +¥1.2 | **菜单价 +¥2** | +1 | **×1.1（慢 10%）** |

- 三两的 +¥2 是**菜单价加成**，玩家只定二两的价 —— 店里就这么写「三两 +2 元」。
- 出碗慢 10%：锅更满，一锅少下几碗。
- 名字尾巴写「（三两）」：`老友牛肉粉（三两）`。

## 4. 三个接线点

```ts
// sim/score.ts —— 主料与份量只加成本，不碰 total
const cost = Math.round((bowlCost(recipe.toppings) + mainCostYuan(mainId) + portionCostYuan(portion)) * 100) / 100;

// sim/customer.ts —— 实收价、满意、出碗
const bowlPrice = state.price + portionDef.priceDelta;
const menuBonus = (mainDef?.satBonus ?? 0) + portionDef.satBonus;
flow.serveCooldown = ... * portionOf(state.portion).serveFactor;

// sim/dish.ts —— 品名读 state.main / state.portion（不再从加料反推）
const parts = { method, main: mainOf(state), noodle, portion: portionSizeOf(state), extras, meal };
```

并加了 `scoreOf(state)`（`sim/dish.ts`）：把粉型/主料/份量一起塞进 `scoreRecipe`，
`state.advanceMinute`、`main.ts` 与替身统一走它，避免四处漏参。

## 5. 替身要会用这两下（否则等于没测）

`game/src/sim/standin.probe.ts` 新增两个决策：

- `pickMain(s)`：在解锁过的主料里挑 `satBonus − costYuan × 1.6` 最高的（替身怕贵）；
- `pickPortion(s)`：排队 ≤1 人时上三两（产能有余量），排起队就回二两。

## 6. 实测（同种子，与 P43 对比）

| 指票 | P43（无主料） | P46（有主料+份量） |
|---|---|---|
| 种子 1 月均营收 | ¥54,912 | **¥92,841** |
| 种子 2 月均营收 | ¥69,989 | **¥74,754** |
| 种子 1 成长 | ×3.77 | ×3.73 |
| 种子 2 成长 | ×4.46 | ×3.76 |
| 种子 1 期末现金 | ¥25,207 | **¥148,384** |
| 加购占营业额 | 0.7%（room 被份量挤掉） | **2.5% / 2.7%**（修好后） |
| 裁决 | PASS_WITH_NOTES | PASS_WITH_NOTES（只剩 T3） |

**一个真坑（测试员抓出来的）**：一开始把份量加价算进「加购 room」——
`room = wallet − (state.price + ¥2)`，结果客人「多要一两粉就买不起加料」，
加购从 5.6% 掉到 **0.7%**。修法：room 只扣菜单价，三点两的客人本来就饿，还会加一份腐竹。

## 8. 已知缺口

- **多款粉同时上菜单**：现在只有「一碗」（`state.recipe` + noodle + main + portion）。
  真店里同时卖七八款（老友粉、老友牛肉粉、老友牛腩粉、干捞、砂锅…），
  顾客按款挑选 —— 这是 `state` 的结构性大改，单独一轮（P47）。
- **主料没有单独图鉴/统计**：卖了多少碗牛肉粉看不到（`tally` 只有总碗数）。
- **建议价只是提示**，玩家调价仍靠手感。
