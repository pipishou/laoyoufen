# 解读层（批 C′）· 2026-11-22

> 方案来源：`docs/本土化与AI能力方案-二次评估-2026-11-22.md` 的批 C′（R6 / R7 修正版）。
> 一句话：**打烊单上除了「明天加什么」，还要说得出「今天为什么」**——并且这句话里的数字是本地算的，AI 只补口气。

## 一、要解决的三个洞

| 缺口 | 原来的样子 | 批 C′ 之后 |
|---|---|---|
| P144 / P146 | 打烊单只有一行钩子，「今天走了 44 位」没有任何解释 | 多出「为什么 · …」一行，按主因分成队满 / 价牌 / 等不及三句 |
| R7 / 菜单盲区 | 只知道总收入，不知道哪一款今天卖不动 | 多出「菜单 · …」一行，一款走得最多 + 一款一碗没动 |
| P247 | 街区胃口（appetite）在界面上完全没有回声 | 吃腻了的时候街坊自己开口，一个月只说一次 |

三句都**不新增状态**：前两句是 `lossSplitOf` 与「日结差分」的读法，第三句是 `districtAppetite` 的读法。

## 二、日结差分（解 R7）

`MenuItem.sold` 是累计数，累计数只会说「老友粉一共卖了三千碗」，玩家从里面读不出今天该改什么。
所以日结时把每款的**当日增量**写进 `DayRecord.menuSold`：

```ts
// game/src/sim/state.ts 的 recordDay，在 state.days.push(rec) 之前
const seen = state.flow.menuSoldSeen ?? {};
const today: Record<string, number> = {};
for (const item of state.menu ?? []) {
  const key = String(item.id);
  const delta = Math.max(0, (item.sold ?? 0) - (seen[key] ?? 0));
  today[key] = delta;
  seen[key] = item.sold ?? 0;
}
state.flow.menuSoldSeen = seen;
if (state.menu && state.menu.length > 0) rec.menuSold = today;
```

两个字段都是**可选**的（`DayRecord.menuSold?`、`CustomerFlow.menuSoldSeen?`），老档天然缺省 —— **不升 SAVE_VERSION，仍是 36**。

## 三、三句话（`game/src/sim/advice.ts`）

| 函数 | 什么时候开口 | 说什么 | 什么时候闭嘴 |
|---|---|---|---|
| `lossWhyOf` | `lossSplitOf` 有主因且当天走人 ≥ 3 | 「今天有 9 位是门口站满了没进来 —— 灶和座总有一个先撑不住。」 | 没主因 / 走人 < 3（少于三位不算一件事） |
| `menuLineOf` | 在架 ≥ 2 款，且有一款卖得动 | 「今天「老友粉」走得最多，「猪杂粉」一碗没动。」 | 只有一款 / 一款都没卖 / 没有日结 |
| `appetiteLineOf` | `districtAppetite < 0.9` 且这个月还没说过 | 「最近不太吃得下大碗了，来一碗小的就好。」 | 胃口 ≥ 0.9 / 本月已说（`markAppetiteSaid` 记账） |

三条都遵守同一条纪律：**在没有可说之处开口，是机器味的第一来源**。所以每个函数都有明确的 `return null` 分支，而不是硬凑一句话。

`menuLineOf` 还处理了一个同名坑：两款同主料同粉型只差配方时，`dishNameOfItem` 会给出同一个名字，
念出来就是「老友粉走得最多，老友粉一碗没动」——这时退回「第 1 款 / 第 2 款」，名字一样的时候，位置才是唯一的区别。

## 五、在线预算（解 R6）

二次评估里算过：`fetchLine` 有 49 个调用点，但 **key 是名词**（`${dim.id}:${tier}`、`ring${ring}`、`def.id`），
同一个 key 有缓存、永不重复 → 成本上限 = **键空间 ≈ 170**，不是「一局 60 次」。

```ts
export const LINE_BUDGET = 200;   // 键空间 170 再留余量
// fetchLine 在缓存命中之后：
if (CACHE.size >= LINE_BUDGET) return null;   // 超了静默走本地句，不报错、不阻塞
```

## 七、与开罗对照

| 开罗 | 位置 | 本作 |
|---|---|---|
| `eat_comment` 4 维 × 9 档 | 客人吃完说一句 | 已有（批 1 的 `tier_voice`，四维九档） |
| `help` 里的「Ramen Stats」 | 静态说明书 | **不做**——说明书是死的，我们要的是当天的话 |
| `balloon` 102 条 | 头顶气泡（情绪） | 已有 `guest_voice` / `guest_talk` |
| 无对应 | 打烊单只说结果不说原因 | **批 C′ 新增**：结果 + 原因 + 菜单，三行同屏 |

开罗不做「解释」，因为它没有流失这个概念（客人不来就是不来了）。
我们的流失是账面数字，不解释就变成「玩家不知道为什么输了」——这是本土化之后必须补的一层。

## 八、新缺口

- **P256**：三句话都是「事后解释」，没有「事前预警」——打烊才说，白天玩家看不见。
- **P257**：`lossWhyOf` 一次只报主因，次要原因（比如队满 9 位、价牌 4 位）被吞掉，玩家可能误以为价签没问题。
- **P258**：`menuLineOf` 只看「卖得最多」与「一碗没动」，不看「卖得动但毛利低」——P232 的加料亏本仍然没人提醒。
- **P259**：预算 200 是键空间估算，没有服务端计数（真打满 200 之后是静默本地句，玩家察觉不到降级）。
- **P260**：`appetite_voice` 一个月只说一次，换区之后重置，玩家可能把「新街区的客人胃口好」误读成「味道变好了」（与 P240 同源）。
- **P261**：`advice_probe.py` 用注入 `dayReport` 的方式验，没有覆盖「真实玩一整天打烊」的路径。
