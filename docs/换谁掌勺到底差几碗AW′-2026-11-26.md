# 换谁掌勺到底差几碗 —— 批 AW′（P472 / P473 / P474 / P475）

> 2026-11-26。上一批（AV′）把「补一个人多卖几碗」从 `tight` 反推改成了**让模型算**，可算的时候只算了「多一个人」，没算**这个人是谁**；
> 那句话里的数字又是 `Math.round`，5.4 与 5.45 都写「5 碗」。这一批把这两件事补齐，顺手把两处各写一遍的「半碗容差」收成一处。

## 一、这一批要解决的四条

| 缺口 | 原文 | 症结 |
| --- | --- | --- |
| **P472** | `cookGain` 只算「多一个人」，不算「这个人的技能」，界面那句话其实跟着技能变 | 补进来的人同时改两条链（并行槽 +1、煮技总和 +skill），模型只按前者折了一下 —— 技能 1 与技能 5 算出同一个数，玩家凭什么多付一倍工钱 |
| **P473** | 「约多卖 N 碗」是 `Math.round`：5.4 与 5.45 都说 5 碗 | 取整规则藏在句子拼接里，没有出处、没有测试；技能高一级带来的那点差别在文案上凭空消失 |
| **P474** | `COOK_GAIN_NOISE = 0.5` 与 `demandBlocked` 的 `+0.5` 是同一把拍子写了两处 | 改一处不改另一处，就会出现「卖不动但值得雇」这种自相矛盾的两句话 |
| **P475** | `capacityWithCooks` 是第五个「当天上限」口径，没进口径表 | 五个入口各算各的，谁也说不出哪个是准的 |

## 二、模型：`staffWithExtraCooks`（`game/src/sim/staff.ts`）

补进来一个人，同时改两条链，所以不能再「折一下」了事：

```ts
export function staffWithExtraCooks(
  state: GameState,
  add: number,
  skill: number,
): { parallel: number; multiplier: number } {
  const extra = Math.max(0, Math.floor(add));
  const stoves = Math.max(1, state.venue.stoves);
  const slotsNow = Math.max(1, cookSlots(state));
  const slotsAfter = Math.max(1, slotsNow + extra);

  const cookSkillNow = sumSkill(state, "cook");
  const cookSkillAfter = cookSkillNow + extra * Math.max(0, skill);
  const grown = staffEffects(state).noodle;
  const perStoveAfter =
    3 + equipLevel(state, "strainer") + Math.min(2, Math.floor(cookSkillAfter / 50) + grown);

  const parallel = Math.max(1, Math.min(stoves, slotsAfter)) * perStoveAfter;

  // 只把煮技那一项换掉，上菜段与专精原样带过去（它们不随「多一个人」变）
  const boilNow = 1 - Math.min(COOK_CUT_MAX, cookSkillNow * COOK_CUT_PER_SKILL);
  const boilAfter = 1 - Math.min(COOK_CUT_MAX, cookSkillAfter * COOK_CUT_PER_SKILL);
  const multiplier =
    boilNow > 0 ? (serveMultiplier(state) / boilNow) * boilAfter : serveMultiplier(state);

  return { parallel, multiplier };
}
```

三条纪律写进注释：① 复用 `sumSkill` / `equipLevel` / `staffEffects`，不另抄一遍公式（抄一遍就会出现「模型说多卖 5 碗、实际卖不动」）；
② **`add = 0` 时返回值必须与 `serveParallel` / `serveMultiplier` 逐位相同**，这条等式钉在测试里；
③ 只替换煮技那一项，上菜段与专精原样带过去 —— 它们不随「多一个人」变。

`capacityWithCooks` 跟着改成：

```ts
export function capacityWithCooks(state: GameState, extra: number, cookSkill = 0): Capacity {
  const now = capacityOf(state);
  const { parallel, multiplier } = staffWithExtraCooks(state, extra, cookSkill);
  const batchMinutes = Math.max(
    0.2,
    (FLOW.serveMinutes * multiplier * stationServeFactor(state)) / parallel,
  );
  const stove = DAY_MINUTES / batchMinutes;
  return pack(stove, now.seats, now.cap, now.demand, now.serveNow);
}
```

`crewFacts` 里这段必须排在挑人**之后**（P472 的实质：先知道是谁，才谈得上多卖几碗）：

```ts
const cookGain = capacityWithCooks(state, 1, hire ? hire.skill : 0).total - now.total;
const cookAddsBowls = cookGain > BOWL_EPSILON;
const why = idle === 0 ? "" : crewWhyWords(kitchenBinds, cookGain, hire ? hire.skill : null);
```

今天没人在问工时传 0 / `null`，落回「多一个人」的说法 —— 不编一个技能等级。

## 三、实测：技能真的进来了，但四道闸还在后面

serve 12 分一碗、4 座、2 灶、`capacity = 999`（临时脚本 `tmp_aw1.test.ts`，跑完已删）：

| 补进来的人 | 加人前灶 | 加人后灶 | 加人后日上限 | `cookGain` | 副句 |
| --- | --- | --- | --- | --- | --- |
| 技能 1 | 30.0 | 62.8 | 62.83 | **32.83** | 补一个技能 1 的师傅，这口灶就烧得上了（约多卖 33 碗） |
| 技能 3 | 30.0 | 69.4 | 65.45 | **35.45** | 补一个技能 3 的师傅……（约多卖 35 碗） |
| 技能 5 | 30.0 | 77.4 | 65.45 | **35.45** | 补一个技能 5 的师傅……（约多卖 35 碗） |

- 座位那一档是 **65.45**（`4 × 120 × 0.9 ÷ 6.6`）：技能 3 与技能 5 都把灶抬过座位，日上限就停在 65.45 ——
  **技能从 3 到 5 不再多卖一碗**，这是四道闸取最小的必然结果，不是 bug。
- 但技能 1（灶只到 62.8）确实比技能 5 少卖 **2.6 碗** —— 这个差以前模型里根本没有。

同一家店压到 serve 6 分一碗（上一批那条 `+5.45` 的配置）：

| 补进来的人 | 加人前灶 | 加人后灶 | `cookGain` | 副句 |
| --- | --- | --- | --- | --- |
| 技能 1 | 60.0 | 125.7 | 5.45 | ……（约多卖 5.5 碗） |
| 技能 3 | 60.0 | 138.7 | 5.45 | ……（约多卖 5.5 碗） |
| 技能 5 | 60.0 | 154.8 | 5.45 | ……（约多卖 5.5 碗） |

灶项本身从 125.7 一路涨到 154.8，可座位只有 65.45 —— 三档差值都是 5.45。
**这条也进了测试**（「技能进了模型，但日上限还被别的闸压着时，差值可以相同」）：
差值相同不代表技能没算进去，只代表今天不是它在卡。

## 四、取整只有一条规则：`bowlGainWords`（`game/src/data/crew.ts`）

```ts
export function bowlGainWords(gain: number): string {
  const n = Math.max(0, gain);
  if (n < 1) return "不到 1 碗";
  if (n >= 9.95) return `${Math.round(n)} 碗`;
  const tenth = Math.round(n * 10) / 10;
  return Number.isInteger(tenth) ? `${tenth} 碗` : `${tenth.toFixed(1)} 碗`;
}
```

| 输入 | 输出 | 为什么 |
| --- | --- | --- |
| 0 / 0.6 | 不到 1 碗 | 0.6 碗写成「1 碗」是假话，写成「0.6 碗」又太啰嗦 |
| 1 / 5 | 1 碗 / 5 碗 | 整数不带小数点 |
| 5.4 | 5.4 碗 | 十碗以内保留一位小数 —— **5.4 与 5.45 从此不是同一句** |
| 5.45 | 5.5 碗 | 同上 |
| 9.95 / 30.2 | 10 碗 / 30 碗 | 这个量级差半碗没人计较 |
| −3（理论上不该出现） | 不到 1 碗 | 负数当 0，不许写「-1 碗」 |

副句随即带上技能（`crewWhyWords(kitchenBinds, cookGain, cookSkill?)`）：

- 有人来问工：`今天卡的就是灶 —— 补一个技能 3 的师傅，这口灶就烧得上了（约多卖 35 碗）。`
- 今天没人来问工：`今天卡的就是灶 —— 补齐人手这口灶才烧得上（多一个人约多卖 4.2 碗）。`（不编技能）

## 七、这一批没动什么

- 日薪表 `WAGE_BY_SKILL`、`COOK_CUT_PER_SKILL = 0.045`、`COOK_CUT_MAX = 0.55`、`inNoodlesNum` 的 +2 封顶、`capacityOf` 的四道闸、`STAGE_MINUTES` —— 一格没动。
- 替身不读 `crewFacts`（`standin.probe.ts` 里不调它），四种子逐位相同是**预期结果**，不是「没生效」的证据；本批的判据在单测与探针截图里。

## 八、新记的缺口

- **P476** 「补一个技能 N 的师傅」这句话假设玩家**能雇到**那个技能的人；今天候选池里只有技能 1 的人时，句子仍然会报「技能 5」（因为挑的是每块钱技能最高那位）—— 候选池与句子之间少一次核对。
- **P477** `staffWithExtraCooks` 只支持「整份技能」累加，不支持「同一个人升级」（`add = 0` 而技能上涨）。
- **P478** `bowlGainWords` 的十碗分界（`9.95`）也是拍的：9.96 写「10 碗」、9.94 写「9.9 碗」，同一档差 0.1 碗却换了语体。
- **P479** `BOWL_EPSILON` 收进 `data/balance.ts` 了，可它既不是 `FLOW` 的一部分、也不在 `resetFlowTuning` 里，容易被当成可调参数。
