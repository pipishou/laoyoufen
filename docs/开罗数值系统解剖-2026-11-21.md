> 目标（m20273）：把开罗的**数值骨架与系统设置**解剖到能照着落地的程度，再逐层对照本作。
> 口径：除「本土化」与「AI」两项外，其余允许照搬开罗 —— 所以这份文档的重点不是「我们不一样」，而是**哪一层该抄、抄成什么数**。

## 0. 结论摘要（先看这五条）

1. **开罗的评分是「四维 × 九档」**。`eat_comment` 是 4 行（味 / 香 / 量 / 气）× 9 档客人评语，说明每根属性最终被压到 0–9 共九档。本作是 0–100 连续分 + S–D 五档 —— **九档这一层可以照搬**，成本极低（只加一层显示映射）。
2. **开罗的合成是加权线性和**。`ramencalc` 的每一项都是 `(汤分 / 阈值) + (面分 / 阈值) + 常数`，再叠乘/叠惩罚项。本作 `total = soup*0.55 + noodle*0.45`，`storeScore = total*0.45 + charm*0.25 + value*0.2 + cost*0.1` —— **同构，无需改骨架**；差别只在开罗把每一维都做成了九档阈值表。
3. **开罗的设备是「并行口数」，不是百分比**。`storeequip` 里灶是 1 口 → 2 口 → 4 口 → 金灶，粉篓是 4 口 → 8 口；价格 250 / 800 / 1,500 / 8,000 KCU。本作设备是「出碗快 15% / 28% / 39% / 48%」的乘数 —— **这是 P117（`capacityGain` 与 `gear.nextGear` 两套口径）的根**：只要改成口数模型，两个函数自然统一，也不用再解释「为什么 5.1 分/碗对不上 HUD 的 2.0」。
4. **开罗有「行情」这一层，本作完全没有**。`economy` 26 条不是剧情，而是**限时全局 buff**：顾客钱包 ±、移动速度 ±、吃速 ±、全品味道/魅力/价格 ±、材料费 ±、四季天气、四类拉面热潮、全场狂热。本作 32 条事件全是「有选项的叙事」，**没有任何一条在改全局乘数**。这是本作数值层最大的结构缺口。
5. **段位费本作偏贵 4 倍**。开罗 11 级审查费合计 8,330,000 KCU ≈ 8,330 碗（按一碗 1,000 KCU）；本作合计 ¥333,000 ≈ 33,300 碗（按一碗 ¥10）。曲线形状都陡，但**总负担差了四倍**，而本作 37 个月就跑完，等于段位费吃掉了绝大部分利润。

## 1. 开罗的七层骨架（按依赖顺序）

```
① 四维属性（味/香/量/气）        ← eat_comment 9 档 × 4 维
        ↓
② 配方合成（汤种 × 面种 × 配料）  ← ramencalc 公式 DSL + 阈值表
        ↓
③ 碗（+1 档到某一维）            ← bowl 5 行
        ↓
④ 定价 ⟷ 顾客钱包 ⟷ 料钱         ← topping 市价/成本 + customer 钱包
        ↓
⑤ 产能（灶口数 / 篓口数 / 座位）  ← storeequip + store_data
        ↓
⑥ 行情（限时全局乘数）           ← economy 26 条
        ↓
⑦ 长期进度（段位 / 竞赛 / 改良 / 投资）← grade_review / rally / custom / investment
```

### 1.1 四维九档 —— `eat_comment`

原文 4 行 × 9 列（9 = 档数）：

| 维 | 第 1 档（最差） | 第 5 档 | 第 9 档（最好） |
|---|---|---|---|
| 味（flavor） | Some might like it. | Addictive flavor. | I taste the universe! |
| 香（aroma） | Aroma's a bit plain. | Smells delicious! | I'm in heaven! |
| 量（volume） | Kind of skimpy... | ...I'm full. | It's never-ending! |
| 气（aura/charm） | Needs more aura. | They really care! | My world changed! |

**[READ]** 行数 4、每行 9 句，第 1 列是固定值 `9`（档数）。
**含义**：开罗玩家看到的不是「味道 73」，而是「这碗的味道让客人说出第几句」。九档是**玩家能感知的最小粒度**，比 0–100 更省心。

### 1.2 配方合成 —— `ramencalc`

原文 8 行（对应 8 种汤种 `s0`–`s7`），每行两段（对应两类面 `n0`/`n1`），段内是 RPN 片段：

```
(s0 / 30) + (n0 / 50) + 2
(s0 / 40) + (n0 / 60) + 2
(s0 / 150) + (n0 / 170) + 2
(s0 / 260) + (n0 / 280) + 2
(s0 / 370) + (n0 / 330) + 2
(s0 / 500) + (n0 / 540) + 2
```

外加惩罚/加成项（同一张表里）：

```
(n2 - 30) / 2          ← 某面型扣分
(s0 * n2) / 500        ← 交叉项
(s0 * 2 * n6) * 100    ← 高阶叠乘
(s0 * 2 * n5) * 25
(s0 * (n4 + 1)) * 50
```

**[READ]** 数字列可见，**[INFER]** 阈值（30/50/40/60/150/170/260/280/330/370/500/540）是「每档对应的分母」而不是价格。
**关键结论**：开罗的分数**不是加权平均，而是「每维除以档宽再相加」** —— 也就是说，一维拉满时贡献约等于一个固定份数，跨档才涨。这解释了为什么开罗的分数总是整数档跳变，而本作是连续小数。
**本作不需要改公式**（`total = soup*0.55 + noodle*0.45` 已经够用），但**可以借它的分母表**：把 soup / noodle / charm 各自映射成 9 档阈值，显示层与 AI 语料都跟着档位走。

### 1.3 配料经济 —— `topping`

37 行（玉米 / 葱花 / 笋干 / 海苔 / 薄切叉烧 / 味付蛋 …），列形如：

```
0  Corn  1  7  0  0  1  1  1  0  1120  80  120  20  30  3  4  3  4  10 13  4  2 ...
```

**[READ]** 位置 9 = `1120`（玉米的基础值，与 `customer` 的钱包列同一位置）；位置 10–13 = `80 / 120 / 20 / 30`。
**[INFER]** 80/120 是**两档售价**（KCU），20/30 是**两档料钱**；后面成对的小数（3 4 / 3 4 / 10 13 / 4 2）是四维贡献的**两档值**。
**换算验证**：80 KCU / 120 KCU 按「一碗拉面 ≈ 800–1,200 KCU」折算，配料价 ≈ **一碗的 8%–15%**；本作配料 ¥0.8–8，一碗 ¥10 → **8%–80%**（顶端偏贵）。料钱 20/30 KCU ≈ 一碗的 2%–3.75%；本作 ¥0.2–3.6 → 2%–36%（顶端偏贵 10 倍）。
→ **结论：本作配料的价格带上沿太宽，37 件里有几件是「单件就吃掉三成料钱」的，应该压成 4 个 tier，tier 决定价格与四维贡献的档数。**

### 1.4 顾客钱包 —— `customer`

90 行。前 6 行：

| 顾客 | 钱包 KCU | 出现权重 | 四维偏好（4 列） |
|---|---|---|---|
| Student | 910 | 10 | 25 / 25 / 0 / 0 |
| Businessman | 1050 | 15 | 0 / 30 / 30 / 0 |
| Boy | 840 | 10 | 35 / 0 / 0 / 35 |
| Clown | 840 | 50 | 0 / 50 / 0 / 50 |
| Dept. Head | 1400 | 15 | 60 / 60 / 60 / 0 |
| Announcer | 1120 | 30 | 88 / 0 / 0 / 88 |

**[READ]** 钱包 840–1400（KCU），权重 10–50，偏好列 0–88。
**换算**：钱包 / 一碗 800–1,200 → **大多数客人只够吃一碗，最富的 1,400 够一碗 + 一份配料**。
**本作现状**：钱包按档位 ×0.85 / 1.0 / 1.35 作用在基础 ¥8–12 上 → ¥6.8–16.2；一碗 ¥10。**同构，且比例更松**（识食的能吃一碗 + 半份配料）。这一层不用改。
**可借鉴**：开罗的「出现权重」跨度 5 倍（10 → 50），本作 `ARCHETYPE` 是均匀的 —— 加权重能让街面「早上多上班族、夜里多酒客」这种**时段感**自然出现（本作 F9 试过 `DAYPART_BIAS`，被替身否决，因为它是**硬偏置**；改成**权重表**就不会动总量，只是换分布）。

### 1.6 产能 —— `storeequip` + `store_data`

**灶（`storeequip` 前 4 行）**：

| 设备 | 口数 | 价 KCU |
|---|---|---|
| 1-Burner Stove | 1 | 250 |
| 2-Burner Stove | 2 | 800 |
| 4-Burner Stove | 4 | 1,500 |
| Golden Stove | 多 | 8,000 |

**粉篓**：`4-Pot Boiler` 4 口 → `8-Pot Boiler` 8 口（650 KCU）→ …

**[READ]** 口数列明确。
**含义**：开罗的产能 = **同时能开几个火 / 煮几篓**，出碗时间 = 单碗时间 / 并行度。这是个**物理模型**，玩家看一眼灶台就知道「我现在只有一口灶」。
**本作**：`STOVE_SERVE_FACTOR` 之类的百分比乘数 + `BENCH_CAPACITY_STEP`。玩家看不到「我几口灶」，只能看到「2.0 分/碗」。
→ **这是最值得照搬的一条**（也是 P117 的解法）：
- 灶档位 = 1 / 2 / 4 / 6 口（对应现有 ¥1,500 / 3,800 / 9,000 / 30,000）
- 案台档位 = 并行备料 1 / 2 / 3 / 4 份（影响 `capacity` 上限与料钱）
- 出碗时间 `serveNow = 单碗时间 / min(灶口, 案台并行)`
- HUD 显示「2 口灶 · 每碗 1.0 分钟」，两个函数（`capacityGain` 与 `nextGear`）都读同一个 `stoveSlots`

**店铺（`store_data`）**：

| 店 | 容量 | 客位（?） |
|---|---|---|
| Main Shop Lv1 | 50 | 20 |
| Main Shop Lv2 | 150 | 40 |
| Main Shop Lv3 | 270 | 90 |
| Main Shop Lv4 | 420 | 150 |

**[READ]** 前两列；**[INFER]** 50/20 = 库存/客席。
**本作**：`BRANCH_SIZES` 4 档 + `EXPANSION` ¥12,000 / ¥35,000（加座）。形状一致（×3 / ×1.8 / ×1.55），**量级也对得上**（我们座位 2 → 3 → 5；开罗客位 20 → 150 是另一个尺度）。这一层不用改。

## 2. 单位：开罗有两套尺度，别混

| 尺度 | 证据 | 换算法 |
|---|---|---|
| **消费侧** | 拉面 800–1,200；配料 80/120；钱包 840–1,400；段位费 5,000–5,000,000；竞赛奖金 1,000–24,000 | 一碗 = 1,000 KCU ↔ 本作 ¥10 → **KCU ÷ 100 = 元** |
| **道具侧** | 灶 250–8,000；投资 5,760–20,250；改良 30,000–270,000 | 与「一碗」不成比例（250 KCU < 一碗 800 KCU），**只能借曲线形状，不能借数** |

`data/balance.ts` 里现有的 `KCU_TO_YUAN = 0.01` 是**消费侧**的，用它乘道具价就会得到「一只碗 ¥600」（已由货币校准那批修掉）。
**规矩（写进代码注释即可）**：消费侧 ×0.01，道具侧按南宁零售锚点定价，**永远不从 KCU 直接乘**。

## 6. 验证方案（每项都要能证伪）

1. **替身 36 月**（种子 1 / 种子 2）：改数值前后对比 `月均 / 日均碗 / 流失 / 段位 / 期末现金`。任何一项掉超 5% 就要回退或调参。
2. **四道数值不变式**（新建 `sim/numbers.test.ts`）：
   - 段位费合计 ≤ 12 个月营收
   - 任一配料价格 ≤ 一碗价 40%
   - 钱包最小值 ≥ 一碗价（最穷的客人也吃得起一碗）
   - 家当合计 ≤ 30 天毛利
3. **bot 三局**：只改数值时，应该看到「流失原因分布」变化，而**不应该**看到「卖出的碗数」大幅波动（那说明改的是产能不是价格）。
4. **九档一致性**：`tier9Of(100) === 9`、`tier9Of(0) === 1`、四维与 total 的档位差不超 2。
