> 依据：`C:\Users\Mo\Desktop\老友粉试玩总结-2026-11-22.md`（18:52 包 `index-DYHcnGRM.js`，saveVersion 35）。
> 那一包里三家机器人照钩子买了 ¥1,500 的猛火灶、又买了 ¥1,500 的汤锅，**第 4 天流失还是 44–50%、卖出的碗数还是 32–38**。

三家座位**全程 2**，日上限 120。HUD 出碗从 2.0 分/碗 降到 1.6 → 1.3，**碗数一动不动**。

## 二、三条根因（本地复现，不是猜）

### 1. 出碗倒计时被整分钟吃掉 —— 所有「出碗更快」的升级都是装饰

`game/src/sim/customer.ts` 的循环：

```ts
flow.serveCooldown = FLOW.serveMinutes * serveMultiplier * equipServeMultiplier * …;
// 下一分钟
flow.serveCooldown = Math.max(0, flow.serveCooldown - 1);
if (flow.serveCooldown <= 0) { /* 出一批 */ }
```

`FLOW.serveMinutes = 1`（`game/src/data/balance.ts` 的 `FLOW_DEFAULTS`）。1 分钟基准乘上任何小于 1 的系数
（灶 0.8167、汤锅、粉篓、巷口洗碗池、碗、配料组合）结果都 ≤ 1 —— 下一分钟一律 `0 - 1 <= 0`，**照样一分钟出一批**。
也就是说：**只有 `serveParallel`（一锅下几碗）是真的，所有「快一点」全是假的。**

复现（当时的 `tmp_ab.test.ts`）：同一局、同一颗种子，买灶与不买灶**逐分钟时间线完全一致**。

### 2. 产能模型把「吃一碗」当成 1 分钟 —— 于是永远说「灶最紧」

`game/src/sim/bottleneck.ts` 里 `EAT_MINUTES = 1`，座位产能算成 `2 座 × 120 分 ÷ (2.2 + 1) = 80 碗`，
而实测一天只有 36 碗。真实吃一碗是 `data/customers.ts` 二十四种客人 `eatSpeed` 的均值 **6.17 分**
（最慢 9、最快 3），2 座一天实际只接得住 `2 × 120 ÷ 8.2 ≈ 29` 碗。

模型口径错了 → `capacityGain().seat(n)` 恒为 0 → **钩子永远不会点「加座」**，只会点灶/汤锅/粉篓。
玩家照做了四天，流失一个点都没降 —— 因为**真正的瓶颈是座位，模型一直在指着灶说话。**

### 3. 加座的东西存在、很便宜，但没人提

`game/src/data/gear.ts` 里早有 `plastic_stool`（塑料矮凳 ¥150，`seats: 1`）与 `bamboo_chair`（竹躺椅 ¥150，`seats: 1`），
`buyGear` 也确实把它们加进 `venue.seats`。但钩子的候选池里只有设备（¥1,500 起）与扩建（¥12,000），
于是「门口站满」的提示永远指向贵八十倍的东西。

顺带一条文案病：事件的「门口借两张凳」是**阿姐借去摆摊**，不是给自己加座；玩家读成加座是合理的误读，这一批改掉了。

## 三、四处改动

1. **出碗改成攒分钟**（`game/src/sim/customer.ts`）
   ```ts
   flow.serveBank = (flow.serveBank ?? 0) + 1;
   const serveInterval = Math.max(0.2, flow.serveCooldown);
   if (flow.serveBank + 1e-9 >= serveInterval) { /* 出一批 */ }
   // 出完之后：serveCooldown = 新间隔；serveBank -= 新间隔（零头留到下一分钟）
   ```
   `CustomerFlow` 加可选字段 `serveBank?: number`（`game/src/sim/state.ts`）—— 老档缺省按 0 起攒，**不升 SAVE_VERSION（仍 36）**。
   0.8 分/碗 的一天是 150 批，1.0 分/碗 是 120 批，提速第一次真的落进碗数。

2. **吃一碗按真实分钟算**（`game/src/sim/bottleneck.ts`）
   `const EAT_MINUTES = 6;`（注释里写清 6.17 的来源）。座位产能从 80 掉到 30 左右，
   `tight` 在新局直接变成 `seats`，`tightWords` 说出「座位坐不下」。

3. **钩子把加座件并入候选池**（`game/src/sim/hook.ts`）
   `capacityPick` 里加一段：把 `GEARS` 中所有 `seats > 0` 且未拥有的家当作为 `kind: "seat"` 的候选，
   增益用 `gain.seat(g.seats)`。队满主因时优先选最便宜的那一件 —— 现在是 **¥150 的塑料矮凳**。
   实测：`先把「塑料矮凳」加上（¥150）`，副行 `今天走了 40 位`。

4. **店铺页把「今天卡在哪」写出来**（`game/src/ui/panels.ts`）
   设备段上方加一行 `[data-tight]`：
   - 卡座位时：`今天卡在座位：塑料矮凳 ¥150 就能多坐 1 位（吃一碗要六分多钟，座位周转不过来）`
   - 其它时候：`今天卡在：灶台出得慢` / `备料不够卖`
   顺手把事件的「门口借两张凳」改成「让阿姐在门口摆摊」，不再冒充加座。

对照校准后的基线（¥109,787 / 201.0 / 41.5% / ¥462,005）：**营收 −12.7%、碗数 −1.3%、流失 +0.8 点、期末现金 −54%**。

读法（诚实记录）：替身是朴素策略，它照钩子买设备却**从不买矮凳**，所以「出碗变快」没换来碗数；
而座位仍卡在 2 座左右时，营收下滑来自「出碗快了、翻台没快」的错位与它多花的钱。
这正好说明这一批的关键：**光把出碗修好不够，玩家还得知道该加座** —— 所以同时把加座写进钩子与店铺页。

## 六、新缺口

- **P262** 替身不会买矮凳，四种子因此看不出这一批的收益；要给替身加一条「座位紧就先买最便宜加座件」的策略，才能量出真实增益。
- **P263** `serveBank` 的零头在打烊时被清掉（不满一轮的进度浪费），一天最多损失一批。
- **P264** 吃一碗 6 分是二十四种客人的均值，但 `eatSpeed` 3 与 9 差三倍 —— 一个九分种的客人占座等于两个人。
- **P265** 店铺页只写「卡在哪」，没写「加这一张能多卖几碗」（缺口 15 碗/日的估算没有显示）。
- **P266** 客人坐满 2 座时「座位」这个词在打烊单里仍是「灶和座总有一个先撑不住」，没点名座位。
