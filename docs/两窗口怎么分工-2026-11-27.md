# 两个窗口怎么展开游戏开发 · 2026-11-27

> 上一份 [决策地图-要不要开并行任务窗](决策地图-要不要开并行任务窗-2026-11-27.md) 回答的是「**要不要**开」，结论是「只值得开一个只读窗」。
> 这一份回答「**怎么**开」—— 把一批的时间线摊开，标出哪一段能交给第二个窗、哪一段交出去就会撞车，并给出可以直接粘过去的开工 prompt。
> 全部数字都是今天在这台机器上**实测**的，不是估计。复现命令在第九节。

---

## 一、一句话结论

**两个窗口的正确分工不是「一人一半写代码」，是「主窗写代码，副窗吃等待」。**

理由只有一条，而且是结构性的：**每批真正要改的源文件只有 10–17 个，其中 `game/src/ui/panels.ts` 最近 12 个 commit 里中了 8 个** —— 两个写窗一起动它，手合一个 1,361 行的函数，冲突率接近 100%。而一批的墙钟里有 **约 40% 是纯等待**（替身 258 秒 + 长跑门 306 秒 + 全量测试 68 秒 + AI 门 47 秒 + 部署 6 分钟），这一段**完全不占主窗的脑子**，正是副窗能吃下的部分。

所以：**副窗做「读、跑、验、查」四件事；主窗独占「写」。**

### 2.1 机器

| 项 | 值 |

| 内存 | **15.4 GB 总 / 1.67 GB 空闲**（实测时刻） |

（上一份决策地图估的 28–30% 是把「读场」也算进去了；读场确实能并行，但它占的是**脑力**不是墙钟，交给副窗要看副窗自己会不会读 —— 见 §6 模板 A。）

### 2.3 并发压测：`probe:standin` + 全量 `vitest` 同时跑

这是最容易撞的一对（两个都在拉 CPU、都在起 node worker）：

| 指标 | 单跑 | 并发 | 变化 |
| --- | --- | --- | --- |
| 替身四种子 | 257.8 s | **268.6 s** | **+4.2%** |
| 全量 vitest | 68.1 s | **86.0 s** | **+26.3%** |
| 空闲内存最低点 | — | **977 MB** | 27 次采样，没被压到换页 |

**结论：这两个可以同时跑。** 短的（vitest）多付 26% 的墙钟，长的（替身）几乎不受影响，内存也没有击穿。
**但**：替身 + 长跑门**不能**同时（BD′ 踩过：长跑门 `fps_min 29.0`，门槛 30；替身一停就是 56.0）。原因是替身把**单核**拉满 258 秒，而长跑门量的是**主线程** fps —— 主线程跟替身抢同一个核。

## 三、一批的时间线，切成「可并行段 / 必须串行段」

以批 BE′（98 分钟）为样本，标出谁能接手：

```
分钟  0 ────── 12 ────── 40 ────── 48 ────── 55 ────── 62 ──────── 75 ────── 90 ─── 98
      │ 读场  │ 写代码  │ 全量测 │ 探针迭代│ 五门   │ 替身+长跑门 │ 文档   │ 上线 │
主窗   ████████  ████████  ░░░░░░  ████████  ░░░░░░  ░░░░░░░░░░░░  ███████  ░░░░
副窗   ░░░░░░░░  ░░░░░░░░  ██████  ░░░░░░░░  ██████  ████████████  ░░░░░░░  ░░░░
```

- **0–12 读场**：主窗必须自己读（要形成判断）。副窗可以**同时**去读另一条线（比如把 100 个 P 编号梳理成表）—— 但那是副窗自己的活儿，不是替主窗读。
- **12–40 写代码**：**副窗绝对不能动源文件**。这一段让它去跑「上一批回归」最划算（`bb/bc/bd/be_probe` 四条一起跑，实测并发 12 秒出结果）。
- **40–48 全量测试**：副窗接手跑，主窗开始写本批探针。
- **48–55 探针迭代**：主窗独占（要改探针、要看看截图）。
- **55–62 五门**：`copy / eye / ai / framediff / debug_exit` 交副窗跑，主窗写文档开头。
- **62–75 替身 + 长跑门**：**这一段的收益最大**。11 分钟里主窗写文档、写 ACCEPTANCE、写账本 —— 全是纯写作，不吃 CPU。
- **75–90 文档**：主窗独占（要写准数字，副窗写的文档主窗还得重写）。
- **90–98 上线**：`push` / `deploy` / 核线上 **只能主窗做**（单 job、单远端）。

**一句话：副窗吃的是「40–48 测试」「55–62 五门」「62–75 双基线」这三段，共约 28 分钟；主窗吃读场、写码、探针、文档、上线。**

## 四、两个窗口的文件分界线（这才是能不能并行的真问题）

### 4.1 白名单：给副窗写，主窗绝不碰

| 路径 | 理由 |
| --- | --- |
| `docs/待办梳理-*.md`、`docs/调研-*.md`（**新建**文件） | 新文件零冲突 |
| `.junshi/handoff/<窗名>.md` | 一人一文件，README 已经定死 |
| `game/data/evidence/prof*/`、`.../regress*/`（**新 slug**） | 只要 slug 不撞，`eye_gate` 清空也只清自己那个 |

### 4.2 灰区：副窗可以**读**，不许写

`game/src/**`、`tools/gate/**`、`game/data/*.json` —— 副窗要读源码才能判断，但**一个字节都不许落盘**。
唯一的例外是「副窗发现了 bug 要写复现脚本」：**必须落在 `tools/gate/.tmp_<窗名>_*.py`**，跑完自己删，不进 git。

### 4.3 黑名单：四件单例，只有主窗能动

| 资源 | 为什么 |
| --- | --- |
| `docs/ACCEPTANCE.md` | 第一节标签链要**整条重排**（当期 → 上一批 → 上上批……）。两个窗各插一行必然连锁错位 —— 批 BE′ 已经踩过一次（`+4` 写成 `+3`，把 `[` 吃掉了） |
| `.junshi/ledger.md` | append-only 1,664 行，两窗同时 append 一定插在同一行号上 |
| `game/src/ui/panels.ts` | **2,159 行，`mountPanels` 一个函数 1,361 行**；最近 12 个 commit 中了 8 个 |
| 部署（`deploy-cli.ps1`） | 远端 `/tmp/sb/NNN.b64` 会撞 —— AGENTS.md 写死了「同时只能有一个 deploy job」 |

### 4.4 实测：每批到底改了几个文件

| 批 | 非证据文件数 | 其中 `panels.ts` |
| --- | --- | --- |
| BE′ `cd119c7` | **10** | ✅ |
| BC′ `f8df14b` | **15** | ✅ |
| BD′ `6a1d0fa` | **16** | ✅ |
| BB′ `c023648` | **11** | ✅ |
| AZ′ `3377001` | **17** | ✅ |
| BB1′ `6b080af` | 60（其中 40+ 是探针批量改） | ✅ |

**10–17 个文件、且 `panels.ts` 每批必中** —— 这就是「两个写窗不可行」的全部证据。不是怕冲突，是**冲突点永远在同一个 1,361 行的函数里**，手合的成本高于并行省下的时间。

## 五、内存 1.67 GB 下的并发上限

实测能同跑：替身（258 s，单核拉满）+ 全量 vitest（112 个 worker）。最低空闲 **977 MB**，没换页。

**但不能这样叠**：

| 组合 | 结果 | 依据 |
| --- | --- | --- |
| 替身 + 长跑门 | ❌ `fps_min 29.0`（门槛 30） | BD′ 实测 |
| 两个窗各跑全量 vitest | ⚠️ 2 × 112 workers，内存会到 500 MB 以下 | 推算（未实测，风险高） |
| 两个窗各起 `vite preview` | ⚠️ 端口撞（4246 已被占 19 个探针） | P520 |
| 两个窗各 `npm run -s build` | ⚠️ 写同一个 `game/dist/`，**「我验的是谁构建的包」无法区分** | 见 P527 |

**安全上限：同时最多 1 个 CPU 长跑（替身 或 长跑门，二选一）+ 1 个短任务（测试/探针/五门）。**

## 七、三种排班，选哪个

| 排班 | 省下的墙钟 | 风险 | 建议 |
| --- | --- | --- | --- |
| **A** 主窗写 + 副窗只读取证 | 0（但主窗读场缩短，间接省 8–12 分钟） | 极低（只写一个新 doc） | ✅ **现在就开** |
| **B** 主窗写 + 副窗跑门与回归 | 约 **25 分钟/批** | 低（副窗不落盘，只跑） | ✅ **主窗写完代码后开** |
| **C** 两个写窗（worktree 隔离） | 约 40 分钟/批 | 高（`panels.ts` 必撞；`ACCEPTANCE`/账本要手合；267 MB 依赖每次手补） | ⛔ 补完 P518 + P520 + P521 再说 |

**推荐组合：A 与 B 复用同一个副窗。** 主窗读场时它梳理待办（A）；主窗写完代码后它转去跑门（B）。这样一个副窗吃满一批里所有「能交出去的时间」，而且**全程不碰源文件**。

## 八、真开两个写窗之前，还差什么（在 P518/P519/P520/P521 之外新记的）

第九节记了四条新缺口（P524–P527），都是今天实测才看清的：

- **P524** 端口没有任何「占用检测」：第二窗起 preview 撞 4246 只会 `strictPort` 直接退出，不会提示「换个端口」。
- **P525** `framediff_probe` 的基准（`game/data/evidence/framediff/baseline`）是**共享单例**：两个窗各自 `--save-baseline`，谁后跑谁说了算，先跑的那批的帧差结论会被静默作废。
- **P526** 「替身不能与长跑门同跑」只写在 `AGENTS.md` 里，是**规矩不是机检**。BD′ 那次假红（`fps_min 29.0`）就是这个规矩没被程序守住。
- **P527** 两个窗共享 `game/dist/`：A 窗 build 出的包会被 B 窗的 preview 读到，「我验的是谁构建的包」无法区分。解法：build 后写 `dist/.build-stamp`（构建时 `git rev-parse HEAD` + 时间），preview 启动时校验。

## 九、复现命令

```powershell
# 机器与内存
(Get-CimInstance Win32_OperatingSystem | Select-Object TotalVisibleMemorySize,FreePhysicalMemory)
Get-Process node | Measure-Object WorkingSet64 -Sum
Get-Process | Sort-Object WorkingSet64 -Descending | Select-Object -First 12 @{n="MB";e={[math]::Round($_.WorkingSet64/1MB,1)}},ProcessName

# 各步耗时（在 game/ 下）
$s=[Diagnostics.Stopwatch]::StartNew(); npx tsc --noEmit; $s.Elapsed.TotalSeconds
$s=[Diagnostics.Stopwatch]::StartNew(); npx vitest run --no-file-parallelism; $s.Elapsed.TotalSeconds
$s=[Diagnostics.Stopwatch]::StartNew(); npm run -s probe:standin; $s.Elapsed.TotalSeconds

# 每批改了哪些文件（非证据）
git show --stat --format="" --name-only cd119c7 | Where-Object { $_ -notmatch "evidence|\.png$" }

# 探针端口分布 / 写死 127.0.0.1 的残留
Select-String -Path tools/gate/*_probe.py -Pattern "127.0.0.1" -SimpleMatch | Measure-Object
Select-String -Path tools/gate/*_probe.py -Pattern "localhost:42" -SimpleMatch | ForEach-Object { ($_.Line -split "localhost:")[1].Substring(0,4) } | Group-Object | Sort-Object Count -Descending
```
