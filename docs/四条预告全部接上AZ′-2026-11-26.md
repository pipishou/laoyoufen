## 一、这一批要解决什么

「手艺树」上第 8–11 段有四张牌挂着 `pending: true`，界面把它们的角标写成「预告」：

| id | 段位 | 界面承诺的原话 | 这一批之前模拟里的真实状态 |
| --- | --- | --- | --- |
| `stove5` | 8 | 设备上限 4 → 5 档 | `PARALLEL_BY_TIER` 的表早写到第 5 档（灶 5 口 / 汤锅 6 口 / 粉篓 7 筒），但 `MAX_EQUIP_LEVEL = 4` 把第五档**锁死** —— 玩家永远买不到 |
| `takeaway` | 9 | 每分钟有一成客人打包带走（不占座） | 全仓只命中 `data/bowl.ts` 的打包碗与 `data/unlocks.ts` 的定义，`sim/` 里**一行都没有** |
| `branch` | 10 | 分店营收并入总账 | `sim/branches.ts` 早就在跑：`recordDay` 第一行 `runBranchDay(state)`，日结单带 `branchBowls` / `branchNet`，`small` 档 `minGrade` 是 8 —— **`pending` 一直是过期的** |
| `legend` | 11 | 所有区能量不再衰减 | `sim/district.ts` 的 `homeEnergyOf` 里没有任何 `isUnlocked(state, "legend")` 判断 —— **只差一个 if** |

四种状态各不相同，但玩家看到的都是同一张标着「预告」的牌。标「预告」看着诚实，实际是「做得比说的少」：
`branch` 是**做完了没说**，`legend` 与 `stove5` 是**数据备好了闸没开**，`takeaway` 是**真没做**。

这一批四条一起算平。验收口径照 GAP 四轮第五节写的四条，一条一条落成判据。

## 二、`stove5`：单出口 `equipMaxLevel`，第五档要第 8 段

### 问题不是「加一档」，是「上限被抄在四个地方」

原来 `MAX_EQUIP_LEVEL = 4` 被抄在四处：

- `sim/equipment.ts` 的 `equipNextCost`（`if (lv >= MAX_EQUIP_LEVEL) return Infinity`）
- `sim/equipment.ts` 的 `buyEquipment`（`if (lv >= MAX_EQUIP_LEVEL) return { ok: false, … }`）
- `sim/hook.ts` 的 `capacityPick`（`if (lv < MAX_EQUIP_LEVEL)`）
- `ui/panels.ts` 的设备行（`Lv ${lv}/4`）

加一档就要改四处，漏一处就出现「面板能点、模拟拒绝」这种人机不一致。所以这一批先收成一个函数：

```ts
// game/src/sim/equipment.ts
export function equipMaxLevel(state: GameState, id: string): number {
  const def = EQUIP_BY_ID.get(id);
  if (!def) return MAX_EQUIP_LEVEL;
  if (!def.unlockLevel || def.unlockLevel <= MAX_EQUIP_LEVEL) return MAX_EQUIP_LEVEL;
  return isUnlocked(state, "stove5") ? MAX_EQUIP_LEVEL_UNLOCKED : MAX_EQUIP_LEVEL;
}

export function equipLockReason(state: GameState, id: string): string | null {
  const def = EQUIP_BY_ID.get(id);
  if (!def || !def.unlockLevel) return null;
  if (equipLevel(state, id) < MAX_EQUIP_LEVEL) return null;
  if (isUnlocked(state, "stove5")) return null;
  const gate = UNLOCK_BY_ID.get("stove5");
  return `第 ${MAX_EQUIP_LEVEL + 1} 档要评到第 ${gate?.grade ?? 8} 段（「${gate?.name ?? "第五档·黄金灶"}」）才换得到`;
}
```

`equipNextCost` / `buyEquipment` / `hook.ts` / `panels.ts` 四处全改读它。数据侧：

- `CAPITAL.equipmentYuan` 从 `[1500, 3800, 9000, 30000]` 变成 **`[1500, 3800, 9000, 30000, 68000]`**（第五档＝开罗的 Golden 系列，¥68,000 ≈ 6,800 碗，约两个月营收）
- 四件 `effects` 各补第 5 句，并各加 `unlockLevel: 5`
- `PARALLEL_BY_TIER` 三段各补一格 → `wok [1,2,3,4,5,6]`、`pot [1,2,3,4,6,8]`、`basket [1,2,3,5,7,10]`

### 两句话不能混：「段位没到」≠「已到顶档」

`equipLockReason` 存在的唯一理由是让这两个状态在界面上分开：

| 状态 | 角标 | 按钮 | meta |
| --- | --- | --- | --- |
| 四档买满、段位没到 | `Lv 4/4` + 「第 5 档未开」 | 灰按钮，写**「段位没到」** | 末尾补「第 5 档要评到第 8 段……」 |
| 评到第 8 段 | `Lv 4/5` + 「黄金灶：炒锅开到 6 口」 | 亮按钮，报 **¥68,000** | 不再提段位 |
| 五档买满 | `Lv 5/5` + 「已到顶档」 | 灰按钮，写「已到顶档」 | —— |

第一版在 `buyEquipment` 里直接沿用旧的 `"已经换到顶档"`，被 `equipment.test.ts` 当场判红：
`expected '第 5 档要评到第 8 段（「第五档·黄金灶」）才换得到' to contain '顶档'`。
这句话对玩家是误导 —— 他会以为设备这条路走到头了。

### 案台第五档 +200，不是 +40

数据表里第五档写的是「日上限 +200 碗」。`buyEquipment` 原来是 `state.capacity += BENCH_CAPACITY_STEP`（40），
照抄的话界面说 +200、账上加 40。所以拆成两个常量：

```ts
if (id === ("bench" satisfies EquipId)) {
  const after = lv + 1;
  state.capacity += after >= MAX_EQUIP_LEVEL_UNLOCKED ? BENCH_CAPACITY_UNLOCKED_STEP : BENCH_CAPACITY_STEP;
}
```

`upgradeLine` 也跟着分支（第五档说「每天多备 200 碗的料」）。

## 三、`takeaway`：打包客不吃座位，但也不动随机流

### 生效点只有两处

```ts
// game/src/sim/customer.ts:335
export function isTakeawayGuest(state: GameState, c: QueueCustomer): boolean {
  return isUnlocked(state, "takeaway") && c.id % 10 === 0;
}
```

① 推进已入座那段：`if (!isTakeawayGuest(state, c)) eatingNow += 1;`
② 出碗内层 while：原来第一行是「座位满了就 break」，现在改成「队头是坐吃的且位子满 → 往后找一位打包的；找不到才 break」。

第一版只改了 ①，漏了 ② ⇒ 打包客永远排在队里等不到窗口，第 9 段的承诺等于零。
②的关键是**不能只判队头**：队头是坐吃的时候，打包客排在第二位也得能被端出去，否则「一成」只在没满座时有效。

### 为什么用 `id % 10` 而不是掷骰子

`arriveOne` 有一条硬纪律（`game/src/sim/customer.ts` 的长注释）：**来一个人固定消耗 4 个随机数**
（常客判定 + 原型 + 档位 + 挑款），无论他最后坐下、看价牌走还是被队满挡住。
多掷一次会让整条 rng 流错位，热卖点火/熄火、36 个月全变 —— 那时我们以为在调打包窗口，其实在掷骰子。

客人 `id` 是单调递增的（`flow.nextId++`），取模十就够「一成」，且同一份存档跑两遍结果一样。
单测钉住：1–100 里正好十位是打包客，未解锁时一位都不算。

### 实测（4/6/8 座，第 8 段 vs 第 9 段，6 天取后 3 天，种子 1）

| 座位 | 卖碗（未开 → 开了） | 队满流失（未开 → 开了） | 座位数 |
| --- | --- | --- | --- |
| 4 | 72.3 → **87.0**（+20%） | 203.7 → **191.0** | 4 → 4 |
| 6 | 115.0 → 126.3 | 171.7 → 168.3 | 6 → 6 |
| 8 | 126.0 → 126.0 | 200.7 → **157.0** | 8 → 8 |

8 座卖不动是正常的：它已经撞到来客天花板（`demandCapOf ≈ 70.6` 那条闸），但走的人少了 44 位 —— 打包窗口对满座店的作用是「少让人走」，不是「多卖」。

## 四、`branch`：`pending` 是过期的，只删标记

## 五、`legend`：只停能量，不停胃口

```ts
// game/src/sim/district.ts
export function homeEnergyOf(state: GameState): number {
  if (isUnlocked(state, "legend")) return 1;
  const age = quarters(state.month - state.districtSince);
  return Math.max(ENERGY_MIN, 1 - HOME_DECAY_PER_QUARTER * age);
}
```

刻意**不碰** `homeAppetiteOf`：开罗 `help.txt` 把 energy（来不来）与 appetite（点多少）分成两条通道，
第 11 段的承诺原话只说了「所有区能量不再衰减」，另一条顺手关掉就是偷偷改经济。

面板上那句「本区客流每季度 −9%」在评到第 11 段之后就成假话了，所以新增一个出口：

```ts
export function energyWords(state: GameState): string {
  if (isUnlocked(state, "legend")) return "本区客流不再往下掉（第 11 段连锁看过来的老客撑住了）";
  return `本区客流每季度 −${Math.round(HOME_DECAY_PER_QUARTER * 100)}%，换区能重新养回满格`;
}
```

——9% 这个数字只在这一处拼，改 `HOME_DECAY_PER_QUARTER` 文案跟着变。

## 六、第十九次「键漏字段」

`ui/panels.ts:2230` 的 shop 缓存键原来没有 `s.month` 与 `s.districtSince`，而换区那一段现在读
`energyWords(s)` 与 `homeEnergyOf(s)`，两者都按「住进这个区多久」算（`month − districtSince`）。

不补键的话：住上四个季度、能量从 1.00 掉到 0.64，面板上的数字**一直是开局那个**；
评到第 11 段之后那句「不再往下掉」也永远不出现。补上 `|${s.month}|${s.districtSince}|`。

这是本系列第十九次同型缺陷（前十八次见账本对应行）。规律没变：**新读一个会随时间变的字段，就要回头看一眼缓存键**。

## 九、新缺口

**P486** `isTakeawayGuest` 用 `c.id % 10`，而 `nextId` 是**跨天不清零**的 —— 长期看比例没问题（每十个一位），
但「一分钟里有一成」这个说法不准（同一位打包客在高峰期与低谷期的分布与来客节奏无关）。
要真做到「每分钟一成」，得引入每分钟的计数，而那会碰 `arriveOne` 的随机数纪律。

**P487** `stove5` 的第五档只给了替身买不到的价格（¥68,000），替身四种子一次都没买它 ——
这一档在替身那条路上等于不存在，只能靠单测与探针证明它接上了。要不要让替身在现金富余时买，
是下一批（BA′「买断的上限」）的同一个问题。

**P488** `data/unlocks.ts` 里 `pending` 字段现在一条都不用了，但字段与 `unlockViews` 里的
`v.pending ? "预告" : "已会"` 分支都留着 —— 下次有人加条目顺手写 `pending: true` 不会有任何提示，
只能靠 `unlocks.test.ts` 那条「pending 长度 0」判红。

**P489** 换区那一段的 `energyWords` 与 `.lmeta` 里那句「客人还吃得下多少也在变：本区每季度 −4%」仍是两段手写，
前者已收成函数、后者还是模板里的字面 —— 与 P451 / P462 同型，只是还没抄第二遍。
