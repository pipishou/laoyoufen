# 智能体团队 vs 多任务窗口 —— 拿数据说话

> 2026-11-28 记。老板已经打开了「使用智能体团队」，问：**团队和多窗口到底该用哪个？**
> 这份不是概念对比，是今晚在本机（Ryzen 7 5800H / 8 核 16 线程 / 15.4 GB 内存 / DSH 0.2.2-rc.5）
> **真跑过的实验**加上本仓四批（BC′/BD′/BE′/BB′）的实测耗时，逐条判出来的。

---

## 一、一句话结论

**这两样东西不在一个层面上，不是二选一。**

- **智能体团队**解决的是「**一个窗里的活怎么分**」—— 主窗（你）派活，子窗（子智能体）真并发干活、把结果压缩成一段话交回来，共享任务板管认领与依赖。**它已经在你的窗里了，随手就能用。**
- **多任务窗口**解决的是「**你自己要同时盯两条不相干的线**」—— 两个完整会话，各自有完整上下文、各自能跟你对话。**它不是并行工具，是并行「你」。**

**所以本仓的答案很干脆：日常批次全部用团队，多窗口只在两个场合开**（见第六节）：
① 需要一个**能跟你对话的**独立视角（比如「你去把 100 个 P 编号梳理一遍，我待会儿问你」）；
② 主窗要跑 4–5 分钟的替身、你不想等 —— 但这条**团队也能做**，所以其实只剩第一条。

---

## 二、两者到底是什么（把容易混的地方摆平）

| | 智能体团队（Team） | 多任务窗口（两个 Session） |
| --- | --- | --- |
| 谁开的 | **我**（主窗）用 `subagent` / `subagent_fork` / `workflow` 派 | **你**在侧栏点「分叉 / 新会话」 |
| 进程 | **同进程**（`subagent-spawn-in-process`，不新增 OS 进程） | **同进程内的另一个 Session**，但**独立上下文与独立 UI** |
| 上下文 | 子窗是干净上下文，只回一段**压缩摘要** | 完整独立上下文，从零开始 |
| 能不能跟你对话 | **不能**（你只能跟我说话） | **能**（那是你的另一个窗） |
| 数量上限 | `maxDepth: 1`（子不能再生子）＋ `maxTasks: 256`（任务板） | 没有硬上限，但每开一个吃一份内存 |
| 互相说话 | `send_message` / `wait_agent` / `interrupt_agent` / 共享任务板 | **裸装说不了话**；要装插件（`parallel_message` / `session_send`）或靠 `.junshi/handoff/` 文件 |
| 工作目录 | 全部同一个 cwd，**改动互相立刻可见** | 同 cwd（分叉继承），也可用 `create_worktree` 隔离 |
| 冲突保护 | 任务上的 `write_scopes` **只是警告，不是锁** | 无（只能靠纪律） |
| 谁做整合 | **我**（主窗读各子窗的返回，写最终答案） | **你**（两个窗各说各的，事实以 git 为准） |

一句话区分：**团队是「一个大脑多双手」，多窗口是「两个大脑」。**
你的问题是「怎么把活干完」，那多半该用手；「我想同时问两个不同的人」才该开第二个窗。

## 三、今晚真跑的实验（这是选型的依据，不是感觉）

### 实验 1 · 子智能体是不是真并发（不是排队）

派两个计时探针，各跑 `Start-Sleep -Seconds 20`，**同一条消息里一起发出去**：

| 探针 | 命令开始 | 命令结束 |
| --- | --- | --- |
| `probe-a` | `08:26:28.721` | `08:26:48.745` |
| `probe-b` | `08:26:28.710` | `08:26:48.745` |

**结论：两个子窗的落地时刻差 11 毫秒，结束时刻同一毫秒。** 40 秒的活 **20.0 秒**做完 —— **真并发，不是排队**。
派发到子窗真正开跑之间，开销约 **3 秒**（我发消息 → 子窗执行第一条命令）。

> 这条很关键：因为「跑替身 258 秒」这种活交给子窗，**墙钟就是 258 秒，不是我干等 258 秒之后才能动**。

### 实验 2 · 团队任务板到底管不管用（CAS 会不会静默覆盖）

| 动作 | 返回 |
| --- | --- |
| `team_task_create` | `{"id":"task-1","revision":1,"status":"pending","ready":true,"owner":null}` |
| `team_task_update` claim（rev 1） | `{"revision":2,"status":"in_progress","owner":"lead"}` |
| `team_task_update` complete（**故意用旧 rev 1**） | **`Error: stale team task "task-1" revision 1; current revision is 2`** |
| `team_task_update` complete（rev 2） | `{"revision":3,"status":"completed"}` |

**结论：CAS 是硬的**，两个窗同时改一条任务不会静默丢写，会明确报 `stale`。这条比 `.junshi/handoff/` 的「约定」实。

### 实验 3 · 子智能体跑真活（替身四种子 258 秒级）时的代价

派一个 `standin-run` 子窗，在 `game/` 里跑 `npm run -s probe:standin`，同时我在主窗写这份文档、量机器。

| 指标 | 子窗闲时（今日基线） | 子窗跑替身时 |
| --- | --- | --- |
| node 进程数 / 内存 | 18 个 / 1,411 MB | **25 个 / 2,363.7 MB** |
| DSH Harness 进程数 / 内存 | 2 个 / 约 2.3 GB | **14 个 / 3,879 MB** |
| 物理内存空闲 | 1.67 GB | **567 MB** |
| 主窗自己的工作 | — | **不受影响**（照常写文件、跑短命令） |
| 替身四种子墙钟 | 257.8 s（单窗跑） | **278.8 s**（子窗跑、我在写文档，+8.1%） |

子窗回报的四行与基线**逐位相同**：

```
[1] ¥136,294 / 235.7 碗 / 34% / ¥303,313
[2] ¥121,201 / 212.9 碗 / 35% / ¥402,821
[3] ¥132,802 / 238.8 碗 / 32% / ¥272,230
[4] ¥137,872 / 244.8 碗 / 33% / ¥358,805   → 均值 ¥132,042 · 233.1 碗 · 33.5% · ¥334,292
```

**结论**：子窗本身几乎不额外占内存（`subagent-spawn-in-process`，不开新进程），
**涨的是它跑的那条命令**（`npm` + `tsx` + `vitest` 的 node 子进程）。真正的硬约束还是那句：
**同一时刻只让一个 CPU 长跑（替身 or 长跑门），别叠第二个。** 空闲掉到 567 MB 时机器已经在换页边缘。
替身在子窗里跑只多花 **21 秒（+8.1%）**，而这 258 秒我并没有干等 —— 这就是团队在「并行」上真正赢的地方。

### 实验 4 · 本仓一批的耗时结构（拿四批 commit 时间戳量的）

| 步骤 | 耗时 | 能不能丢给子窗 |
| --- | --- | --- |
| 读场（读源码取证） | 8–12 min | **能，而且最适合**（子窗读完只回结论，我的上下文不涨） |
| 写代码 | 25–35 min | 不能（要一手拿捏，见第四节） |
| `tsc --noEmit` | 2.0 s | 能，但没意义 |
| 全量 `vitest --no-file-parallelism` | 68.1 s | **能** |
| `npm run -s build` | 1.7 s | 能，但没意义 |
| 单个探针 | 8.4 s | 能（两个并发 12.1 s，不打架） |
| `eye_gate shot` | 15.0 s | 能 |
| `framediff_probe` | 16.9 s | 能（**但基准是共享单例，P525**） |
| `ai_gate` | 46.7 s | 能 |
| **`probe:standin` 四种子** | **257.8 s** | **能，最值钱的一条** |

而**团队赢**，因为它在同一个窗里，不用你切窗口、不用你复制粘贴、跑完自动把结论送回来。

## 六、本仓的推荐：主力用团队，多窗口只开一个场合

### 6.1 常态：一个窗 + 团队（推荐，今天就能这么干）

按本仓每批的八件交付物排：

| 阶段 | 谁做 | 怎么派 |
| --- | --- | --- |
| 读场（AGENTS / ACCEPTANCE / 账本 / 源码） | **子窗 ×1–2** | `subagent` 只读，回来只要「结论文档 + 行号」 |
| 写代码（数据→模拟→界面→接线） | **主窗** | 不派（要一手拿捏数值纪律） |
| 全量测 + 五门 | **子窗 ×1** | 派一条命令串，回来只要「红/绿 + 失败行」 |
| 替身四种子（258 s） | **子窗 ×1** | 派完我继续写文档 |
| 长跑门（306 s） | **子窗 ×1**，**必须等替身回来再派** | 写进任务描述：`blocked_by: 替身那条` |
| 探针迭代 | **主窗** | 要快速来回改，不派 |
| 文档 / ACCEPTANCE / 账本 / 部署 | **主窗** | 全是单例，不派 |

**用任务板把「先后」写死**：`probe:standin` 与 `playthrough_gate` 建成两条任务，后者 `blocked_by` 前者 ——
这就是把 `AGENTS.md` 二·五那条「替身不能与长跑门同跑」的**规矩**变成**机检**（顺手解 P526）。

### 6.2 多窗口只在一种场合开

**「需要一个能追问的独立视角」**，典型就是老板昨天问的那种活：

> 「去把 101 个 P 编号、四份决策地图、五份手册全部读一遍，梳理成一份『还剩什么』的清单，我待会儿问你细节。」

这种活用子窗也能做（`subagent` 返回一段摘要），但只要**你要追问**，就得有第二个窗 —— 因为子窗不能被追问（`send_message` 只能续一次，且它不记得你看不见的细节）。

**别为「并行」开第二个窗**：今晚的实验 1 已经证明子窗是真并发，第二个窗在「并行」上**一点没赢**，只赢在「能对话」。

### 6.3 团队 + 多窗口的组合（真要用的话）

主窗（带团队）写代码 + 副窗只读调研，两边靠 `.junshi/handoff/` 与 git 对齐，
副窗别碰 `panels.ts` / `ACCEPTANCE.md` / 账本 / `evidence/` / `game/dist/`（六个单例，见 `.junshi/handoff/README.md`）。
副窗跑探针用 **4247** 端口（4246 主窗占着）。

## 七、硬约束与坑（这些比结论重要）

1. **`maxDepth: 1`**：子窗**不能再派子窗**。想「一个子窗管三条活」，得用 `workflow`（`workflow-ptc` 引擎，`provider: spawn`），它一次扇出几十个 worker；或者干脆我自己派三条。
2. **`write_scopes` 只是警告**：`team_task_create` 里写的作用域**不进锁**，两个 owner 同时写一个文件照样互相覆盖。判据在纪律，不在机制。
3. **Team 不隔离目录**：`dsh-tool-agent-team` README 原话「Team 不创建隔离工作目录、不跨进程协调，也不自动释放任务所有者」。要隔离得 `create_worktree`。
4. **任务变更不会叫醒 idle 的子窗**：改了任务不会自动让它动，必须 `send_message`。任务板是「记录」，不是「闹钟」。
5. **子窗不会被暂停**：`wait_agent` / `interrupt_agent` 是让**我**等 / 让子窗**停**，不是队列控制。
6. **团队任务板在**进程内**：DSH 重启就没了（与 P528 同型）—— 跨重启要落 `.junshi/handoff/` 文件。
7. **子窗跑长活不要把 CPU 拉满两条**：实验 3 里空闲降到 567 MB，同时叠替身 + 长跑门就会重演 BD′ 那次 `fps_min 29.0` 假红（P526）。
8. **不要指望子窗「记得」**：每个子窗是干净上下文，系统提示占 3–5 K，交接细节必须写在 prompt 里，别用「你懂的」。
9. **fork 与 spawn 不同**：`subagent_fork` 继承我这整段对话（适合「接着刚才的分析往下」），`subagent` 是干净的（适合「去查一件事」）。两者都 `continuable`，都能 `send_message` 续。

## 九、这一节留的缺口

记账编号接着 `docs/ACCEPTANCE.md` 第五节往下走（P530 之后）。

- **P531** `write_scopes` 只是警告、不进锁：两个 owner 同时写同一文件会静默互相覆盖。**解法定**：派活时由主窗自己保证不重叠（一张「本轮谁写哪个文件」表），或等 P518 拆完 `panels.ts` 再谈真并行。**判据**：一批活派给 3 个子窗，事后 `git diff` 里没有任何一个文件被两个 owner 改过。
- **P532** 团队任务板**不跨重启**（进程内），而 P528 的 `parallel_hold` 也不跨重启 —— 两套协调机制在「重启」这一格上都失效。**解法定**：主窗收尾时把任务板导出到 `.junshi/handoff/tasks-<日期>.json`（`team_task_list` 全量），重启后人工对账。**判据**：重启后 `.junshi/handoff/` 里能查到上一轮未完成任务。
- **P533** 子窗跑完回的是**摘要**，「它到底查了哪几行」无法复核；要复核只能让它把证据落文件。**解法定**：派读场活时强制「结论必须带 `文件:行号`，写进 `docs/<slug>-证据.md`」。**判据**：每份读场结论都能用 `grep` 在源码里对上。
- **P534** 长跑门与替身的串行关系目前靠人在 prompt 里写「等它回来再派」，任务板的 `blocked_by` 只是**记录**、不会阻止 agent 提前动。**解法定**：派活脚本先 `team_task_list` 查 blocker 状态，未完成就拒派。**判据**：故意提前派一次，被明确拒绝而不是跑起来。
