# DSH 多窗口操作手册（2026-11-27）

> 起因：老板用侧栏的「分叉」开了第二个窗（`老友粉游戏迁移开发评估 -2`），问「在 dsh 下怎么进行联动操作」。
> 这份文件回答三件事：**哪些「并行」是真的**、**两个会话窗之间怎么传话**、**真要同时写代码该怎么隔离**。
> 全部结论来自本机实测（DSH 0.2.2-rc.5，profile `desktop`），不是推测。

---

## 一句话结论

**DSH 里的「联动」有三层，只有第一层是即时的、工具级的；你现在开的第二个会话窗属于第二层，只能靠共享文件和 git 传话；第三层（worktree）解决的是「两个窗同时写代码」的隔离。**

| 层 | 谁和谁 | 能不能即时传话 | 靠什么 | 什么时候用 |
| --- | --- | --- | --- | --- |
| **A** | 一个会话内的多个 agent（`subagent` / `subagent_fork` / Team 任务板） | **能**，工具级 | `send_message` / `wait_agent` / `team_task_*` | 一件事可以切成互不重叠的几块，且都需要「读代码 + 写代码」 |
| **B** | 两个独立会话窗（你现在这种） | **不能** | `.junshi/handoff/*.md` + `git log` | 想让另一个窗做只读调研，或者自己盯着一条独立线索 |
| **C** | 两个会话窗，各写各的目录 | 不能（同上） | `git worktree` | 真的要并行写代码（本项目目前不建议，见第五节） |

---

## 二、A 层：同一个会话内的多 agent（真·即时联动）

这一层不需要开新窗，**在当前这个窗里就能用**，工具已经在手上：

| 工具 | 干什么 |
| --- | --- |
| `subagent` | 起一个干净的子 agent（不继承本会话上下文），干完回一段结果 |
| `subagent_fork` | 起一个**继承本会话已完成轮次**的子 agent，适合「接着我的上下文去审/去查」 |
| `list_agents` | 看整棵树（`lead` + 每个子 agent 的状态） |
| `send_message` | 给某个还活着的子 agent 追加指令 / 继续对话 |
| `wait_agent` | 等消息或等完成，不空转 |
| `interrupt_agent` | 让它停下当前工作（可以之后再用 `send_message` 接上） |

**Team 模式额外给四个任务板工具**（`team_task_create` / `team_task_list` / `team_task_get` / `team_task_update`），让 Lead 把活分下去、子 agent 自己认领。

### 打开 Team 模式（默认是关的）

1. 在这个会话的**模型与推理等级菜单**里打开「**使用智能体团队**」。
2. 开完之后，Subagent 页头会多一个入口，同一面板上方是成员、下方是共享任务板。
3. 选择会保存（`team/mode` 事件），重启后仍有效。

也可以改 profile 让新会话默认开：`@deepseek-ai/dsh-agent-team` 的 `defaultEnabled: true`。

### 边界（必须知道，否则会白等）

- Team 任务板属于**一棵 subagent 树**，不是「多个会话窗的公共板」。侧栏另开的窗看不见它。
- Team **不创建隔离工作目录**、**不跨进程协调**、**不自动释放任务所有者**。
- 写作用域只是**建议**，不是锁。两个子 agent 同时写 `panels.ts` 照样会互相覆盖。
- 任务就绪**不会**自动把 owner 叫醒 —— 要 `send_message` 通知它。

## 三、B 层：两个会话窗之间（你现在开的这种）

### 事实

你在侧栏开的第二个窗是**独立 Session**：

- 它的 `list_agents` 里看不见我，我的里也看不见它；
- 我的 `send_message` 发不过去，反之亦然；
- 但**工作目录是共享的**（同一个 `D:\项目\REA\REA\重构\老友粉店`），**git 仓库是同一个**。

所以两个窗之间只有两条通道：**共享文件** 和 **共享 git**。

### 已经落盘的做法：`.junshi/handoff/`

```
.junshi/handoff/
├── README.md     ← 规则（谁写哪个文件、单例资源归属）
├── TEMPLATE.md   ← 模板（照抄改）
└── lead.md       ← 主窗（本窗）的交接状态
```

**操作步骤：**

1. 在新窗里让 agent 读 `.junshi/handoff/README.md` 和 `TEMPLATE.md`。
2. 让它 `write` 自己的文件，比如 `.junshi/handoff/fork2.md`，填四段：我在做什么 / 写到哪 / 需要你给什么 / 我不碰什么。
3. 两窗各自只写自己的文件，**读别人的文件只读不写**。
4. 代码状态**永远以 git 为准**：`git log --oneline -5`、`git status --short`、`git diff --stat`。文字说「我改了 X」而 git 里没有，就是没改。

### 必须点名的单例资源

两个人同时写必然打架，交接时写清归属：

| 资源 | 为什么 |
| --- | --- |
| `docs/ACCEPTANCE.md` | 第一节标签链要整条重排，两窗各插一行会连锁错位 |
| `.junshi/ledger.md` | append-only，1,664 行 |
| `game/data/evidence/<slug>/` | `eye_gate` 会清空整个目录 |
| `game/src/ui/panels.ts` | 2,159 行，最近 12 个 commit 有 8 个动了它 |

### 两个不能同时跑的东西

`npm run -s probe:standin`（替身四种子，约 576 秒，单核拉满）和 `playthrough_gate --minutes 5`（长跑门）**撞主线程**：BD′ 踩过，长跑门首跑 `fps_min 29.0`（门槛 30）假红，替身一停单跑就是 56.0。两窗分工时先看对方交接文件的「我现在在做什么」。

## 四、C 层：真要并行写代码 —— `git worktree`

### 本仓库实测

```
git worktree add .agents/worktrees/<名字> -b <分支名>
```

- 建出 **1,940 个文件**，几秒完成；
- 起点是 HEAD，未提交的改动**留在主检出**（这点很重要：`.junshi/handoff/` 这种新文件不会跟过去）；
- `node_modules` **不会**跟过去 —— 主检出 `node_modules` 4.4 MB / 259 文件，`game/node_modules` **267 MB / 5,602 文件**，都在 `.gitignore` 里。

### 所以建完 worktree 还要补依赖

```powershell
$repo = "D:\项目\REA\REA\重构\老友粉店"
$wt   = "$repo\.agents\worktrees\<名字>"

# 方式一：真装一份（占 267 MB，但两个窗完全独立）
cd $wt\game; npm ci

# 方式二：junction 借主检出的依赖（省 267 MB，只能跑读/测试，不要两个窗同时 install）
New-Item -ItemType Junction -Path "$wt\game\node_modules" -Target "$repo\game\node_modules"
New-Item -ItemType Junction -Path "$wt\node_modules"      -Target "$repo\node_modules"
```

### 收工

```powershell
cd "D:\项目\REA\REA\重构\老友粉店"
git worktree remove .agents/worktrees/<名字> --force   # 丢弃未提交改动时加 --force
git branch -D <分支名>                                  # 分支确认不要了再删
```

`.agents/worktrees/` 是**目录池**，插件首次创建时会自动在里面放一个 `.gitignore`（内容是 `*`），所以池子本身不会被提交。

### 在 DSH 里让 agent 自己建 worktree（插件）

本机**已装但未启用**两个包：

| 包 | 干什么 |
| --- | --- |
| `@deepseek-ai/dsh-experimental-worktree` | 服务：建命名 worktree 并把**调用方 Session 的 cwd** 切过去 |
| `@deepseek-ai/dsh-experimental-tool-worktree` | 给模型的 `create_worktree` 工具（依赖上面那个） |

**启用步骤**（改一个文件 + 重启）：

1. 备份 `C:\Users\Mo\.dsh\profiles\desktop\cordis.patch.yml`。
2. 在文件**末尾**追加：

```yaml
- insert:
    - id: worktree
      name: '@deepseek-ai/dsh-experimental-worktree'
    - id: tool-worktree
      name: '@deepseek-ai/dsh-experimental-tool-worktree'
```

3. 重启 Desktop（或 `dsh --profile desktop`）。
4. 插件页确认多出「Git 工作树」卡片；对话框里多出 `create_worktree` 工具。

**注意**：以后若改用 `@deepseek-ai/dsh-experimental-forge-bundle`（一个开关同时给「变更请求与工作树」面板 + `create_worktree`），**必须先把上面这两条删掉**，否则 `worktree` / `tool-worktree` 两个 id 重复插入，对应控件会变成只读。

`create_worktree` 的行为：从本地 commit / 分支 / tag 拉一个新分支和检出、**把本 Session 的 cwd 切过去**、未提交文件留在原处、同名直接失败、没有 fetch。要回来用 `working_directory` 切回原目录（检出和分支都还在）。

## 五、对「老友粉店」这个仓库，建议怎么用

`docs/决策地图-要不要开并行任务窗-2026-11-27.md` 已经把数字算过：一批 96–160 分钟里，纯等待占 **27–30 分钟（28–30%）**，但两个写代码的窗会撞在 2,159 行的 `panels.ts` 上（最近 12 个 commit 有 8 个动它），而每批八件交付物里后五件（探针 / 文档 / ACCEPTANCE / 账本 / 部署）全是全局单例。

**所以：**

- ✅ **值得**：主窗写代码，第二个窗**只读**（梳理 100 个 P 编号、翻开罗取证、写新建的 `docs/` 文件）。主窗跑替身那 9.6 分钟、长跑门那 5–6 分钟，正好是它的工作窗口。
- ⚠️ **有条件**：真要两个窗同时写代码，先补 **P518**（`panels.ts` 按页签拆开）。拆分之前，`git worktree` 只能隔离「写的是不同文件」的批次。
- ❌ **不要**：三个以上窗同时跑 `npm ci` / `vitest` / `probe:standin`；部署也不能并行（两个 deploy job 会撞远端 `/tmp/sb/NNN.b64`）。

## 七、记成缺口

- **P521** `create_worktree` 建出来的检出没有 `node_modules`（267 MB），每次都要手补 —— 可以在插件配置里加一步「创建后跑 `npm ci` 或建 junction」，目前得靠人记。
- **P522** 两个会话窗之间没有任何工具级的通知；`.junshi/handoff/` 是约定不是机制，靠人（或 agent）自觉写。若以后真常态并行，需要一个「谁在看谁的文件」的小工具。
