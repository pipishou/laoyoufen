# 试玩二轮评估与优化方案（2026-11-19）

> 输入：`docs/老友粉试玩总结-2026-11-19.zip`（pack 23 / pack 24 四局，bot 试玩）
> 本文只做**二次确认 + 评估 + 方案**，不动代码。改不改、先改哪批，见第七节。

## 一、一句话结论

五条观察点里，**两条是真缺陷（红标与钩子在次日失效、产能钩点名了成本件），一条是设计误判（座位才是街边摊的硬顶），两条是文案与手感**。
报告给的「买灶后流失没降」是对的，但根因不是「座位不够」这么笼统——是**钩子从第二天起就不再指向产能**，以及**红标从来没亮过一次**。

## 三、五条观察点：报告结论 vs 二次确认

### 观察点 1 · 打烊单底部那行字会不会读完

**报告**：会抢眼但不稳；前缀「明天先处理 ·」+ 主句自带「明天先把…」叠了两个「明天」；主句偏长把「今天走了 N 位」挤到下一行；金色「明天继续 ›」紧挨着抢点击。

**二次确认**：成立。代码在 `game/src/sim/hook.ts:87-90`：
```ts
const head = state.cash >= pick.cost ? `明天先把「${pick.what}」加上` : `明天卖了钱先添「${pick.what}」`;
text: `${head}（${yuan(pick.cost)}）—— 今天走了 ${lost} 位`
```
前缀在 CSS（`hud.css` 的 `.dayhook::before` / `.dayhook.bad::before`）。两处各写一次「明天」，是文案层的问题，不是逻辑。

**评估**：要改，成本极低（0.2 天）。主句不该再带「明天」——前缀已经说了。

### 观察点 2 · 看到「明天先处理 · 加灶」会不会去买

**报告**：会，四局全买了点名的猛火灶第 1 档。

**二次确认**：成立，且**这条是 A/B 批最成功的地方**。钩子做成了「具体到件 + 具体到价 + 给出理由（今天走了 N 位）」，四个不同打法的玩家都照做了。

**评估**：不改。

### 观察点 3 · 买完灶后第 4 天流失有没有掉下去

**报告**：没有，三局第 4 天仍在 53%–57%；结论是「座位才是硬顶」。

**二次确认**：**现象成立，根因判断需要修正。**我在代码里复现了两件事：

**（a）产能钩从第二天起就消失了。**
`game/src/sim/hook.ts:82` 的产能分支依赖 `lostRateOf(state)`，而 `lostRateOf` 优先读 `state.dayReport`：
```ts
const rep = state.dayReport;
const lost = rep ? rep.lost : state.flow.lostToday;
const served = rep ? rep.served : state.flow.servedToday;
```
`state.dayReport` 在玩家点「明天继续」时被 `ackDayReport()` 清成 `null`（`game/src/sim/state.ts:865-868`），而 `flow.lostToday / servedToday` 在 `endDay()` 里已清零 —— 于是**第二天一早流失率恒为 0**。
实测（临时用例，已删）：

```
atClose= 0.6   nextMorning= 0
hookAtClose  = capacity | 明天先把「猛火灶（第 1 档）」加上（¥1,500）—— 今天走了 60 位
hookNextMorning = gear   | 明天添一件「塑料矮凳」（¥100）
```

同一处失效也解释了**观察点 5**：`game/src/ui/panels.ts:461` 的红标判定是
```ts
const hot = lostRateOf(s) >= CAPACITY_LOST_RATE ? " hot" : "";
```
玩家看红标是在**第二天早上的店铺页**，那一刻流失率已经是 0 —— 红标一次都没亮过。报告说「红标根本没亮」，是对的，而且不是 CSS 问题，是数据断了。

**（b）钩子点名了粉篓，粉篓不是产能件。**
`game/src/sim/hook.ts:68-77` 的 `capacityPick()`：把「三件设备下一档」和「下一档扩建」全部丢进候选，**按价格升序取最便宜**：
```ts
return picks.sort((a, b) => a.cost - b.cost)[0] ?? null;
```
买完猛火灶第 1 档（¥1,500）之后，粉篓与汤勺第 1 档也是 ¥1,500 且排在前面 → 钩子稳定改口「粉篓」。实测：
```
pick= 明天先把「粉篓与汤勺（第 1 档）」加上（¥1,500）—— 今天走了 60 位
```
而粉篓在商店里的说明是「一碗省 ¥0.14」——**它降的是单碗成本，对「一天最多出多少碗」毫无帮助**。真正能接住排队的是「打通隔墙 ¥12,000（座位 +2）」，偏偏因为最贵，永远排不到。

**评估**：这是本轮**唯一必须修的设计错误**。要改，两个根因各 0.5 天以内。

### 观察点 4 · 副行那句 AI 口吻像不像南宁人

**报告**：句子本身像；问题是会**自己改字**，且有时与主句对不上（主句卖粉篓，副行却说「先整灶台再理座位」）。

**二次确认**：两条都成立，而且都能定位。
- **改字**：`game/src/main.ts` 的 `prefetchHookLine()` 在 AI 回来后调了 `refresh()` —— 打烊单还开着，文字就被换掉了。先本地句、再远端句，是 P62 已记录的已知现象，但在「玩家正在读的一句话」上发生，性质从「加载」变成了「内容不稳定」。
- **对不上**：`hook_voice` 本地池只有 6 句（账本 P74），且**不按 kind 分池** —— 卖粉篓（产能）和卖矮凳（家当）共用同一个池，当然会撞。小陆第 3 天那句「先整灶台再理座位」是池里第 1 句恰好撞上。

**评估**：要改，且是「性价比最高的一处体感提升」：分池 + 不让它当场改字，1 天内能做完。

### 观察点 5 · 高流失日的两个红标会不会太抢眼

**报告**：无法判断，因为红标根本没亮。

**二次确认**：成立，原因见观察点 3(a)。另有一处设计缺口（账本 P75）：家当里「巷口洗碗池 ¥800 / 大砧板 ¥900 / 冰柜 ¥3,600」同属产能侧，即使修好也不会被标。

**评估**：根因修完红标自然会亮；家当那一层顺手补。
