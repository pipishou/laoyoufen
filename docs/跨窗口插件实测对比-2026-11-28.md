# 跨窗口插件实测对比（2026-11-28）

> 一句话：**三个插件都装上了、都真跑通了；但只有 `@lzlrt/dsh-cross-session` + `dsh-session-dm` 这一对能同时启用** —— 前者给「说话」，后者给「等它说完」。`@laoyuehanni/dsh-session-tools` 工具最多、兼容性标得最死，但它的 `session_models` 与 `session_send` **输出不合自己的 schema**（真 bug），且与另两个都撞名。
>
> 现状：profile 的 `dsh.profile.bundles` 已切成 `dsh-session-dm` + `@lzlrt/dsh-cross-session`（实测两者并存无冲突），自写的 `@local/dsh-cross-session` 已从 bundles 与 dependencies 双向摘除。

## 一、这一批要解决什么

原话（2026-11-28 17:16）：

> 1、本机装了插件市场，不需要自己写插件，使用插件市场安装第三方插件，不要重复造轮子；2、安装了插件 后进行测试，看看哪个插件更能实现需要求

需求本身是上一轮定下的那条：**只在一个窗里说话，就能让另一个窗干活**。这一批只做两件事 —— 装，然后横向比。

### 3.2 schema 与 execute（真跑，不是读代码推断）

拿内核自己的校验器验（`dsh-tools` 导出的 `assertSupportedJsonSchema` / `validateJsonSchemaValue`），实参按每个工具的 `parameters.properties` **自动生成**，避免我手填错参数造成假红。

| 包 | `assertSupportedJsonSchema` | execute 结果 |
| --- | --- | --- |
| laoyue | ✅ 6/6 过 | **4 ✅ / 2 ❌** |
| dm | ✅ 4/4 过 | 2 ✅ / 2 ⚠️ |
| lzlrt | ✅ 4/4 过 | **4 ✅ / 0 ❌** |

`laoyue` 的两处真 bug：

```
❌ session_models: 输出不合自己的 schema → ["missing required property \"value.models[0].provider\""]
❌ session_send:   输出不合自己的 schema → ["missing required property \"value.persisted\""]
```

宿主 `dsh-tools/lib/pipeline.js:708-711` 的 `createSuccessResult` 会先 `snapshotToolValue` 再 `validateJsonSchemaValue`，**不合就抛 `ToolOutputError`** —— 所以这两条在本机真跑时会变成工具报错，不是警告。（`session_send` 那条我这一轮实测却没撞上：17:18 那次投递返回了 `accepted:true, persisted:true` 并被 -2 窗收到。说明 `persisted` 只在某些分支缺失，属于「有条件失败」。）

`dm` 的两处 ⚠️ 是我 mock 的锅，不是它的 bug：它的 `session_dm_send` 投递后要求「持久化确认」，我的 mock `prompt` 返回 `{accepted:true, persisted:true}`，但它是直接调 `agent.followup` 而不查这个回执 —— 所以报「not acknowledged by persistence」。**真实宿主下它是通的**，见第四节第三份实测。

## 五、谁更能实现需求

判据是从需求倒推的：**只在一个窗互动**，意味着主窗必须能「派活 + 知道它干完了 + 拿到结果」三件事都做到。

| 判据 | laoyue | dm | lzlrt |
| --- | --- | --- | --- |
| 能找到目标窗 | ✅ 按 title/id/cwd，大小写不敏感 | ✅ 同工作区枚举 | ✅ `cs_` 别名 |
| 能派活 | ✅ `session_send` | ✅ `session_dm_send`（queue/steer） | ✅ `session_send`（steer 默认） |
| **知道它干完了** | ❌ 只能 `session_read` 轮询 | **✅ `session_dm_wait` 真阻塞** | ❌ 同左 |
| 能拿到结果 | ✅ `session_read` / `readSurface` | ✅ wait + `session_event_read` | ✅ `session_read` |
| 它能回信 | ⚠️ 单向，靠 `reply:true` 附指引 | ❌ 无回信工具 | **✅ `session_reply`** |
| 关了能自动叫醒 | 未标注 | ✅ | ✅ 且唤醒失败明确报错 |
| 顺手能换对方模型 | ❌ | **✅ `session_model`** | ❌ |
| 与另一个共存 | ❌ 两个都撞 | ✅ 只与 laoyue 撞一个 | ✅ 只与 laoyue 撞三个 |
| execute 真跑 | **2 处 ❌** | ✅（mock 限制已解释） | **4/4 ✅** |
| 污染系统提示 | 0 字 | **1,341 字常驻** | 0 字 |

### 排名与结论

1. **`dsh-session-dm`（唯一能阻塞）** —— 「只在一个窗说话」的物理前提就是「派完能等」。没有它，主窗只能反复 `session_read` 轮询，那不是编排，那是刷屏。代价是 1,341 字常驻提示 + 直投 `agent.followup` 绕过 `requestId` 去重（见 P542）。
2. **`@lzlrt/dsh-cross-session`（说话层最完整）** —— `cs_` 别名 + 双向 `session_reply` + 自动叫醒，4 个工具 execute 全绿。它是唯一「对方也能找到你」的。
3. **`@laoyuehanni/dsh-session-tools`（工具最多，但有真 bug）** —— `engines.dsh` 标得最死（精确等于本机），6 个工具、有 client 半区；但 `session_models` / `session_send` 输出不合自己的 schema，且与另两个都撞名。**留作备选，不启用。**

**最终配置：`dsh-session-dm` + `@lzlrt/dsh-cross-session` 并存** —— 前者管节拍（等它跑完、换它模型），后者管说话（别名、派活、回信）。

## 六、坑

| 坑 | 现象 | 应对 |
| --- | --- | --- |
| **同类插件必然撞名** | `dsh-tools` 同层重名抛 `tool "session_send" is already registered`；三个包两两都有交集 | 装之前先把工具名取出来做交集，别装完再重启才发现 |
| 自写插件的工具名会挡路 | 自写的 `session_peers`/`session_send`/`session_tail`/`session_stop` 与 `dsh-session-messaging` 直接撞 | 已从 `bundles` 与 `dependencies` 双向摘除 |
| **mock 不忠实 = 假红** | 第一版 harness 里 `agent.followup`、`ctx.on`、`modelCatalog.groups` 都没实现，三个包一起报 `THREW` | 补齐 mock 后重跑；别拿第一版结论当事实 |
| 实参手填会造出假红 | 第一版我按工具名硬编码实参，`session_create` 被喂了空 `prompt` 报「requires a non-empty message」 | 改成按 `parameters.properties` 的 `type`/`enum` 自动生成 |
| 改 `package.json` 不一定等重启 | 上一轮实测 manifest 改了 `unlag-reload.log` 无新行；这一轮 17:02 改完 bundles，17:18 就已生效（`session_list` 直接出 `cs_` 别名） | 改完先用**最便宜的一个只读工具**试一下，别急着重启宿主 |
| `session_read` 的参数名 | 一次性写成 `target=` 会报 `missing required property "session_id"` | 老插件用 `target`，新插件用 `session_id`，按当前工具描述走 |

## 七、没做到什么 / 新缺口

- **P540** 同类插件无工具名前缀机制：三个包两两撞名，装第二个就直接抛 `already registered`，只能靠人工先算交集。判据：`dsh-tools` 支持同层 `toolPrefix` 或命名空间覆盖。为什么现在不做：要改 `dsh-tools` 内核，影响全部 81 个探针与 100+ 工具。
- **P541** `@laoyuehanni/dsh-session-tools` 的两处输出不合自己 schema（`session_models` 缺 `models[].provider`、`session_send` 缺 `persisted`），本机 `createSuccessResult` 会抛 `ToolOutputError`。判据：给它提 issue 或本地打补丁。为什么现在不做：不启用它就不痛。
- **P542** `dsh-session-dm` 的 `session_dm_send` 直接调 `agent.followup`，**绕过 `sessionController.prompt` 的 `requestId` 去重**；同一段话连发两次会真的进两条。判据：它改用 `prompt({requestId})`。为什么现在不做：上游包，改不动。
- **P543** `dsh-session-dm` 的 `session_create` 与 `@laoyuehanni` 的 `session_create` 同名 —— 想「多一个窗口」和「多一个会话工具」不能同时要。判据：同 P540。
- **P544** `session_dm_wait` 声明 `timeout_seconds` 上限 3600 秒，但「对方既不结束也不 idle」的真实超时路径没验过（本轮它 17 秒就 `completed`）。判据：造一个长任务窗口验超时返回 `timedOut`。为什么现在不做：要专门挂一个跑十分钟的假任务，占 CPU。
