## 一、结论先说

| 路 | 能不能「只在一个窗说话」 | 实测定论 |
| --- | --- | --- |
| 自带 `list_agents` / `send_message` / `wait_agent` / `interrupt_agent` | **不能** | 只在**当前 Session 的 subagent 树**里寻址。`list_agents` 只返回 `lead` + 本窗自己的四个子窗（`ccgs-research` / `probe-a` / `probe-b` / `standin-run`），**看不见侧栏那个 -2 窗**。 |
| 自带 `team_task_create` / `team_task_list` | **不能** | Team 任务板属于**一棵 subagent 树**，不是多窗公共板。实测 `team_task_list` 只返回本窗那条 `task-1`。老板两个窗都开了 Team，也是各开各的板。 |
| 自带 `schedule_create` | **不能** | 工具的 `TARGET_CHOICES = ['this_session','new_once','new']`（`dsh-tool-schedule\src\index.ts:228`），`targetFor()` 里 `if (target === 'this_session') return { kind:'session', sessionId: agent.session.id }`。**存储层支持任意 Session**（`ScheduleTarget` 的 `session` 分支注释原文「Deliver to one existing Session that is not a delegated child.」），但模型面与 UI 面都只给「当前对话」。 |
| 第三方 `dsh-parallel-sessions` / `dsh-tool-session-message` | **理论能，本机装不上** | 两个都**没发 npm**（`registry.npmjs.org` 404）；`git ls-remote` 实测 `Recv failure: Connection was reset` 与 `Connection timed out after 300059 milliseconds`。GitHub 这条路在本机是硬墙。 |
| **自己写本地插件** | **能** | 见下文。不走网络、不依赖 GitHub、四个工具，已装进 profile。 |

## 二、写了什么

包在 `D:\项目\skill\dsh-cross-session`，四个文件：

| 文件 | 作用 |
| --- | --- |
| `package.json` | `type: module`、`exports: {".": "./index.js"}`、`dsh.bundle.patch: "./cordis.patch.yml"`、`engines.node >= 20`、`private: true` |
| `cordis.patch.yml` | 四行：`- insert:` → `{ id: cross-session, name: '@local/dsh-cross-session' }`（**无 config**，限流与上限写成 index.js 常量） |
| `index.js` | 409 行，只 import `node:crypto` |
| `README.md` | 七节：为什么要有它 / 四个工具 / 安全边界 / 装法 / 自检 / 已知限制 |

**为什么不 import `@deepseek-ai/dsh-tools`**：profile 的 `node_modules` 下**没有** `@deepseek-ai` 目录（那条路径只在安装目录里）。插件里 import 内核包会装不住。工具的 `parameters` / `output.schema` 用纯对象手写，靠内核的 `register()` 校验。

### 四个工具

| 工具 | 干什么 | 参数 |
| --- | --- | --- |
| `session_peers` | 列**同 cwd 的顶层会话**（不含自己、不含子 agent、不含别的 cwd），带标题 / 是否开着 / 忙闲 | 无 |
| `session_send` | 给对方发一句话 | `session_id` / `message` / `mode`（`queue` 默认 = 排成对方下一轮；`steer` = 插进对方下一步） |
| `session_tail` | 读对方最近几条发言 | `session_id` / `limit`（默认 3，上限 20） |
| `session_stop` | 叫停对方当前这一轮（不丢排队消息） | `session_id` |

### 走的是三个现成服务，一个新东西都没造

```js
scoped.sessionQuery.listSessions()                 // 列会话（带 header.cwd / live）
scoped.sessionQuery.readTitleSnapshots([...ids])   // 批量取标题
scoped.sessionQuery.filterEvents(id, [{ kind:'type', values:['assistant/message','user/message'] }])
scoped.agents.get(id)?.status                      // 'idle' | 'running'
scoped.sessionController.prompt({ requestId, sessionId, mode,
  content: [{ type:'text', text: body }], clientTimeZone: 'Asia/Hong_Kong' }, signal)
scoped.sessionController.cancel({ sessionId })     // 只对 live agent 有效
```

**`prompt` 的形状是硬要求**（`dsh-api-session-controller\lib\index.js:4145`）：
`requestId` 必填（漏了会被包成 `session/agent-busy: prompt rejected`）；`content` 必须含非空白文本；`clientTimeZone` 要么不给、要么是合法 IANA 名。

### 安全边界（写进代码里，不是口头约定）

- 只认 `header.cwd` **字符串完全相等**的会话；
- **两边任一方 cwd 为空就一律不认** —— 空 cwd 是全表默认值，凭它认邻居会把不相干的会话拉进来；
- `header.origin === 'subagent'` 或 `delegationDepth > 0` 一律排除；
- 单条消息上限 **32 KB**（`Buffer.byteLength`），超了直接拒；
- 同一目标 **2 秒一条**（限流表在进程内存，重启即清，与 P528 同型）；
- `session_stop` 只对**开着**的会话有效，离线直接返回「没开着」，**不会替它冷启**（`commands.cancel` 里 `const agent = this.ctx.agents.get(...)` 是同步取，不走 `resolveAgent`）。

### 3.1 `test-offline.mjs` —— 60 条断言全过

不启 DSH，直接 `import` 内核 `dsh-tools/lib/index.js` 的 `assertSupportedJsonSchema` / `validateJsonSchemaValue`，干四件事：

1. 四个工具的定义能过 `register()` 的五条校验（`output.render` 是函数、`output.schema` 过子集校验、`parameters` 是完整 JSON Schema、没占用 `run_code`）；

### 3.2 `test-compose.mjs` —— profile 组合验过

用 `dsh-app-boot` 的 `loadProfile('dsh','desktop', INSTALL_ANCHOR, home)` + `composeEntries` 把 profile 真组合一遍：


同时确认关键服务都在：`agent` / `session-query-sqlite` / `tools` / `agent-loop` / `session-controller`（`@deepseek-ai/dsh-api-session-controller`，**挂在 `dsh-web-app` 层，不在 base**）/ `agent-team` / `tool-agent-team`。

> **踩过的坑**：`loadProfile` 的签名是 `(binName, name, installAnchor, home, options)`，第一版按 `(dir, name)` 调，报 `profile "dsh" does not exist`（`dsh-app-boot\lib\index.js:1855`）。

### 3.3 `parameters` 的坑（最贵的一条）

`dsh-tools\lib\index.js` 的 `register()`（`:433`）**不调 `defineTool`**，所以插件手写的 `parameters` 会被**原样当 JSON Schema 用**。它**不是** `defineTool` 里那种「隐式 property map」。

- 写错的样子：`parameters: { session_id: { type:'string', required:true } }`
- 写对的样子：`parameters: { type:'object', properties:{ session_id:{type:'string'} }, required:['session_id'], additionalProperties:false }`

判据：`additionalProperties` 必须是显式 boolean（`shared-DGx6D7zk.js:171`），`required` 必须是字符串数组且都在 `properties` 里。

## 六、没做到什么（新缺口 P535–P539）

- **P535**：`session_send` 会把**离线**会话冷启（走 `sessionController.prompt` → `resolveAgent` → `resume`）。好处是「关了的窗也能叫起来」，坏处是主窗分不清「它本来就在跑」与「我刚把它叫醒」——`status` 只给 `idle`/`running`，没有「刚被唤醒」这一档。
- **P536**：限流表 `lastSendAt` 在**进程内存**，重启即清；且它是**全局共享**的，不是 per-caller —— 两个窗同时给第三个窗发话会互相挤占额度。
- **P537**：`session_tail` 只能读到 `assistant/message` 与 `user/message` 的**文本块**。它跑了什么命令、改了哪几行，**读不到**（`extractSessionEventText` 对 `reasoning` 直接丢弃、`tool/call` 只留名字与参数）。验收仍要它自己报 `文件:行号`（与 P533 同型）。
- **P538**：两个窗共享同一 cwd 与同一批文件，**没有任何写入隔离**。`session_send` 能约定「你别碰 X」，但拦不住（与 P531 的 `write_scopes` advisory 同型）。
- **P539**：cwd 必须**字符串完全相等**，比 P530 更硬 —— 只要哪天在新窗里 `cd game`，`session_peers` 会直接返回**空表**（不是报错，是空表），容易误判成「没有别的窗」。**用法约束**：起 preview 用工具的 `workdir` 参数，别改会话 cwd。
