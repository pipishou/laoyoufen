# 批 AR′：灶要有人掌勺（P449 的一半）

2026-11-26 · 上一批 [AQ′](./一句话只有一个出处AQ′-2026-11-26.md) · 当期验收指针 [ACCEPTANCE.md](./ACCEPTANCE.md)

## 一、P449 其实是两条

上一批留下的说法是「『厨房真卡』的配平只活在测试里」。这一批先做取证，量完发现它得拆成两条：

1. **数值这条**：真实配平下，厨房**永远不会**成为瓶颈。开局灶位 360 碗/天、来客 70 碗/天，差五倍。
   要让厨房真卡，得把 `FLOW.serveMinutes` 抬到 3 分以上 —— 那时的流失率是 50%+，卖碗数反而掉。
   **这条不改**：改它等于把游戏变难，而且和「小店起步」的调子相反。
2. **说法这条**：灶位买了第二口、第三口，**在数值上一格都不涨**，因为没有人掌勺。
   界面上从来没有任何一句话说过这件事 —— 玩家花了钱，看不出为什么没用。**这条本批就解。**

## 二、真实配平下的三闸实测

做法：`createInitialState("p", seed)` → 改座位 / 灶位 / `FLOW.serveMinutes` → 跑满 6 天，取后 3 天均值，种子 1/2/3。

### 座位与灶位

| 配置 | 卖出 | 走掉 | 模型 tight |
| --- | --- | --- | --- |
| 座 6 · 灶 1 | 111.3 | 128.5 | seats |
| 座 6 · 灶 2 | **111.3** | **128.5** | seats |
| 座 6 · 灶 3 | **111.3** | **128.5** | seats |
| 座 8 · 灶 1 | 114.1 | 61.8 | demand |
| 座 8 · 灶 2 | **114.1** | **61.8** | demand |
| 座 8 · 灶 3 | **114.1** | **61.8** | demand |

灶位从 1 加到 3，卖出与走掉**一个数字都没动**。

### 出碗节拍（6 座 / 8 座）

| `serveMinutes` | 座 6 卖出 / 走掉 | 座 8 卖出 / 走掉 |
| --- | --- | --- |
| 0.5 | 111.3 / 128.5 | 114.1 / 61.8 |
| 1（默认） | 111.3 / 128.5 | 114.1 / 61.8 |
| 2 | 105.0 / 137.3 | 112.7 / 81.9 |
| 4 | 82.6 / 126.5 | 87.4 / 128.5 |

**加快出碗不增销量**，只减少走掉的人；**放慢出碗会掉销量**。也就是说厨房从来不是闸，快慢只是让队短一点。

这份实测已经钉成测试 `game/src/sim/kitchen-never-binds.test.ts`（5 例）：6 座 × 灶 1–4 口共 24 格全部 `tight !== "stove"`、灶量是来客量的两倍以上、压慢到 6 分才会轮到灶 —— 哪天有人动了 `FLOW.serveMinutes`、并行槽或区客流，它先红。

## 三、为什么加灶没用：`cookSlots` 卡着

`game/src/sim/staff.ts`：

```ts
export function cookSlots(state: GameState): number {
  return 1 + state.staff.roster.filter((m) => m.role === "cook" && !m.resting).length;
}

export function serveParallel(state: GameState): number {
  const stoves = Math.max(1, state.venue.stoves);
  return Math.max(1, Math.min(stoves, cookSlots(state))) * inNoodlesNum(state);
}
```

开局 `cookSlots = 1`，于是 `Math.min(stoves, 1)` 恒等于 1 —— 买第二口灶，并行度还是 3（1 口 × 3 篓）。

grep 全仓 `掌勺|开火`，只有两处命中：`game/src/ui/panels.ts:702` 的「人手已经招满」和 `:1077` 的包装线说明。**没有一处告诉玩家「灶要有人掌勺」。**

## 四、`crewFacts`：一句事实，不劝买

新建 `game/src/sim/crew.ts`：

```ts
export interface CrewFacts {
  stoves: number;
  slots: number;
  idle: number;   // 没人看的灶位
  words: string;
}

export function crewFacts(state: GameState): CrewFacts {
  const stoves = Math.max(1, state.venue.stoves);
  const slots = Math.max(1, cookSlots(state));
  const idle = Math.max(0, stoves - slots);
  const words = idle === 0
    ? `灶位 ${stoves} 口，能开火 ${slots} 口 —— 人手够，每一口灶都烧得上`
    : `灶位 ${stoves} 口，眼下只有 ${slots} 个人掌勺 —— 第 ${slots + 1} 口起没人看，火开不起来`;
  return { stoves, slots, idle, words };
}
```

三条纪律写在文件头：

- **只说事实**：几口灶、几个人、第几口起空着。
- **不劝买、不给价钱、不算账**：不出现 ¥、「划算」「建议」「推荐」。
- **不重复别人的话**：招人页已经有「人手已经招满」，这里只说灶。

第一版文案写的是「买来的灶都烧得上」，被 `crew.test.ts` 的第四条判据（不匹配 `/¥|元|买|推荐|建议|划算/`）判红，改成「每一口灶都烧得上」。

## 五、两处同源

`game/src/ui/panels.ts` 两个页面都读同一句 `crew.words`：

- **店面页**：`shopHtml` 里 `equipHint` 之后、`一碗分成三段` 那行**之前**，插 `<div class="lmeta crewline" data-crew-idle>`。
- **店员页**：`staffHtml` 的段标题之后，同一句话加句号。

只在 `idle > 0` 时出现；人手够的店看不到这句。

**第十五次「键漏字段」预防**：shop 缓存键补了 `|${crewFacts(s).idle}|` —— 不加这格，买灶之后 DOM 不重画，探针 `three_stoves_warns` 会红。

## 八、还欠什么

- **P449 只解了一半**：界面说清了「为什么加灶没用」，但**没给玩家一条把灶用起来的路**（招人的价钱、招几个才够、ROI 是多少，仍然散在招人页里）。真要让玩家算这笔账，得单开一批把「灶—人—座位」三者的回本口径对齐。
- **P458**（新）：`crewFacts` 只说「几个人掌勺」，没说「再招一个人每月多少工钱、能多开几口灶」。玩家知道卡在哪，仍不知道贵不贵。
- **P459**（新）：`kitchen-never-binds.test.ts` 只是把现状钉住，不是「厨房应该永不卡」的论证 —— 真出问题时它会红，但红的时候没人知道该改哪里。
- **P460**（新）：这句警告只在店面页与店员页，打烊单与钩子副行没有它（与 P448 之前同型）。
