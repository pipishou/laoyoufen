# 批 AO′：厨房还会不会更慢，以及「抬了也卖不动」要说出来

2026-11-26 · 解 P446 + P447 · 只改说法与测试口径，不动一个数值

---

## 一、这两条缺口是同一件事的两面

批 AN′ 把「一天最多卖几碗」按实测重算之后，留下两条：

- **P446**：出碗与案台的增益仍是**三道闸**口径（灶 / 座位 / 总闸），回答的是「厨房这段还卡不卡」。
  可来客封顶的店里，「厨房还卡不卡」与「今天能不能多卖」是两件事 ——
  八座时灶 360 碗、座位 131 碗、备料 200 碗，来客只有 70 碗。
  这时面板若还写「哪一段最慢就添哪一段」，玩家会照买，买完一碗不多。
- **P447**：P445 把出碗主循环从「一分钟只判一次」改成「一分钟最多判六批」，
  可在默认配平下出碗节拍压根不是瓶颈（**灶 360 碗 vs 来客 70 碗**），
  所以这个修法**用卖碗数根本验证不了**。

这两条其实是一条：**没有一个「厨房比来客慢」的配平，就既说不清增益为什么是 0，也验不了 P445。**

## 二、先造出「厨房真的卡」的对照配平（解 P447）

办法不用新配平表：临时把 `FLOW.serveMinutes` 抬上去，出碗节拍就慢下来，厨房立刻成为瓶颈。
测量口径：`createInitialState("p", seed)` → `s.venue.seats = N`、`s.capacity = 9999`、`s.reputation = 500`、
`s.totalCustomers = 5000`，连跑 6 天取后 3 天均值，种子 1/2/3。

| `FLOW.serveMinutes` | 模型 `stove` | 模型 `total` / `tight` | 实测 8 座 | 实测 24 座 | 差 |
| --- | --- | --- | --- | --- | --- |
| 1（默认） | 360 | 130 / **demand** | 111.4 | 115.8 | 模型 +12%（卡的是来客） |
| 3 | 120 | 120 / **stove** | 112.9 | 113.8 | −6.2% |
| **6** | **60** | **60 / stove** | **58.6** | **58.6** | **−2.4%** |
| 12 | 30 | 30 / **stove** | 29.0 | 29.0 | −3.4% |

三件事一眼看清：

1. **AN′ 的灶项公式是对的**：把厨房压慢之后，实测碗数与 `120 / 出碗分钟` 三档都吻合到 6% 以内。
2. **默认配平下不是厨房的事**：`serve=1` 时模型给 130，实测 111–116，差的那 12% 全是来客量在管。
3. **座位在这四档里都不是闸**：`seat(1)` 恒为 0 —— 与 AN′ 的「座位增益含天花板」一致。

落进 `game/src/sim/capacity-model.test.ts` 的那条用例就是上表 `serve=6` 那一行：

```ts
const before = FLOW.serveMinutes;
try {
  FLOW.serveMinutes = 6;
  // …八座、口碑 500、累计 5000、总闸 9999
  expect(c.tight).toBe("stove");
  expect(Math.abs(c.total - 58.6) / 58.6).toBeLessThan(0.08);   // 实测 58.6
  expect(capacityGain(s).stove).toBeGreaterThan(5);             // 这时抬灶真有用
} finally {
  FLOW.serveMinutes = before;   // 必须在 finally 里还原，否则并行跑会串到别的用例
}
```

这条用例的价值不在「58.6 这个数」，而在于：**从此 P445 那个改动有了一个能用卖碗数说话的配平**。
以前它只能保证「节拍压到地板时不会退化成 1 分钟一批」，现在能保证「厨房真卡时，一天该出多少就是多少」。

## 三、P446：把「抬了也卖不动」说出来

### 模型侧（`game/src/sim/bottleneck.ts`）

`capacityGain` 多返回一个布尔：

```ts
const demandBlocked = now.tight === "demand" && gateBase > now.demand + 0.5;
```

两个条件必须同时成立：

- `tight === "demand"`：今天卖多少由街上进来的人数决定；
- `gateBase > now.demand + 0.5`：三道闸（灶 / 座位 / 总闸）**还高出半碗以上** ——
  要是三道闸恰好压在来客量上，抬闸其实还能多卖，这时候不能说「卖不动」。

这是一个**只读事实**，不参与任何数值。

### 界面侧（`game/src/ui/panels.ts`）

设备段那句提示原来写死：

> 哪一段最慢就添哪一段，添别的会被最慢那段吃掉。

现在按 `capacityGain(s).demandBlocked` 换：

> 今天这三段再添也卖不动 —— 灶、座位、备料都还有富余，卡在街上进来的人就这么多。
> 想多卖，得让街上更热闹：修街面、比赛赢过同行、把口碑养起来、换个人多的区。

为什么这么写：

- **不许再说「添哪一段」**：玩家的处境是「添了也没用」，再给祈使句就是骗钱。
- **要给去处**：只说「卖不动」是死路。真正能抬来客量的恰好是已有系统（街面 / 对手 / 口碑 / 换区），
  这些都不是新机制，只是把手指指过去。
- **不动一个数值**：这条分支只换字符串。

### 第十五个「键漏字段」（本轮踩到）

店铺页的缓存键里没有 `demandBlocked`。加座位之后状态变了、`tight` 从 `seats` 变 `demand`，
可这份键只看 `seats` 的数字与 `capacityGain` 之外的那些字段 —— 结果**DOM 不重画，提示还停在旧说法**。
探针 `blocked_appears_at_eight` 首跑就是红的。

修法：在 `panels.ts` 的 shop 缓存键里补 `${capacityGain(s).demandBlocked ? 1 : 0}`，
顺手把 `s.reputation` 与 `s.totalCustomers` 也塞进键（这两项直接决定来客量，之前同样漏着）。

## 五、这一批没动什么

- **没有改任何经济数值**：`EAT_MINUTES` / `SEAT_IDLE` / `pack()` / `demandPerDay` 一格没动。
- **没有让钩子改主意**：`nextHook` 的顺序与阈值不变。八座时钩子本来就不提产能（批 AM′ 的
  `capacityPick` 在 `helpful` 为空时 `return null`），本批只是让**面板那句提示**跟钩子一致。
- **没有替 P445 加新机制**：P445 的修法早就落了，本批只是给它造了一个能用碗数验证的配平。

## 六、新缺口

- **P448**：`demandBlocked` 只用在设备段一句提示上。打烊单、钩子副行、案台那一行**都还没有**这句话 ——
  玩家可能先在打烊单上看到「先把『塑料矮凳』加上」，再翻到店铺页看到「再添也卖不动」，两处仍是两条口径。
- **P449**：厨房那条对照配平只活在测试里（`FLOW.serveMinutes = 6` 加 `try/finally`）。
  游戏里没有任何一处会把 `serveMinutes` 抬到那个量级，所以**玩家永远不会遇到「厨房真卡」的处境** ——
  P445 的收益对玩家是零，只有测试受益。
- **P450**：`demandBlocked` 的 `+0.5` 是拍的（半碗容差）。为什么不是 1 碗或 5%，没有依据，只够挡住浮点噪声。
