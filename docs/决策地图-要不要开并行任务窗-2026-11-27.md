# 决策地图：要不要再开任务窗同步开发（多窗口并行）· 2026-11-27

> 一句话：**可以开，但只值得开「一个只读调研窗」；写代码的窗口开两个就已经撞在同一份 2,159 行的 `panels.ts` 上。** 现在并行省下的是 25–30% 的等待，赔进去的是合并冲突加双份的读场成本。

这页不是凭感觉写的。下面两组数字都是从仓库里量出来的：一批的墙钟拆解（`git log` 的 commit 时间 + 各门实测耗时），和最近 12 个 commit 的文件热度。

---

## 一、实测：一批的时间到底花在哪

拿刚做完的三批（BB′ / BC′ / BD′ / BE′）的 commit 时间戳算墙钟：

| 批 | 起点 | 终点 | 墙钟 |
| --- | --- | --- | --- |
| BB′ | 10:43（前一批 BB1′ 09:18） | 10:54 | **约 96 分钟**（含 BB1′ 的门复跑尾巴） |
| BC′ | 12:20 | 12:36 | **约 97 分钟** |
| BD′ | 15:16 | 15:32 | **约 160 分钟**（含一次长跑门假红重跑） |
| BE′ | 16:54 | 17:06 | **约 98 分钟** |

再把这 98 分钟拆开（都是本批实跑过的耗时，不是估）：

| 步骤 | 实测耗时 | 能不能和别的窗口并行 |
| --- | --- | --- |
| 读场（AGENTS.md + ACCEPTANCE + 账本三行 + 相关源码 4–8 个文件） | 约 8–12 分钟 | **能**（纯读） |
| 想判据 + 写代码（数据表 → 模拟 → 界面 → 接线） | 约 25–35 分钟 | 只在文件集不相交时能 |
| 单测迭代（`npx vitest run --no-file-parallelism`，70–115 秒 / 次） | 约 5–10 分钟 | **不能**（占满 CPU，跑了会互相拖慢到假红） |
| 构建 `npm run -s build` | 约 30 秒 | 不能 |
| 探针迭代（Playwright，`be_probe` 29 条约 1–2 分钟 / 次） | 约 5–8 分钟 | 不能（同一个 preview 端口） |
| 五门（`copy_gate` / `eye_gate` / `ai_gate`） | 约 4–6 分钟 | 不能（`eye_gate` 会清空 slug 目录） |
| **替身四种子** `npm run -s probe:standin` | **约 576 秒（9.6 分钟）** | 不能（单核拉满，跑长跑门会假红成 fps 29） |
| **长跑门** `playthrough_gate --minutes 5` | 约 5–6 分钟 | 不能（同上，AGENTS.md 二·五已经写死这条） |
| 文档 + ACCEPTANCE + 账本 | 约 8–10 分钟 | 只在「账本按批分文件」之后能 |
| 部署 `deploy-cli.ps1`（421 块 base64 上传） | 约 6 分钟 | 不能（同时只能一个 job） |

**纯等待合计约 27–30 分钟，占一批的 28–30%。** 剩下 70% 是「读、想、写、排错」——只有「读」和「写」这两段可能并行。

## 二、写冲突在哪（实测，不是假设）

最近 12 个 commit 里，每个源文件被改了几次：

| 文件 | 被改次数 | 体量 | 冲突后果 |
| --- | --- | --- | --- |
| `game/src/ui/panels.ts` | **8 / 12** | **2,159 行**，其中 `mountPanels` 一个函数就 1,361 行 | 两个窗口同时改 → 手工合并 1,361 行的巨型函数，diff 冲突率极高 |
| `game/src/data/unlocks.ts` | 4 | 137 行 | 好合（表格式，一行一条） |
| `game/src/sim/invest.ts` | 4 | 298 行 | 中等（函数粒度过关） |
| `game/src/main.ts` | 3 | 1,503 行 | 中等（action 注册表是追加型） |
| `game/src/sim/crew.ts` + `game/src/data/crew.ts` | 各 3 | — | 好合 |
| `game/src/data/manual.ts` | 3 | — | 好合，但**手册不许写阿拉伯数字**这条断言会撞 |
| `game/src/ui/hud.ts` / `hud.css` | 2 / 2 | 885 行 / 2,325 行 | 中等 |

四批里 `panels.ts` 全中（AZ′ / BA′ / BD′ / BE′）。**原因是结构性的：这个游戏的每一批最终都要有一个「玩家看得见」的落点，而所有面板都在同一个文件里。**

单文件热区之外，还有三处**单例资源**：

1. `docs/ACCEPTANCE.md` —— append-only 单一文件，第一节的标签链（「当期最后一批 / 上一批 / 上上批 ……」）需要**整条重排**，两个窗口各插一行会连锁错位（本批已经踩过：`+4` vs `+3` 把 `[` 吃掉了）。
2. `.junshi/ledger.md` —— 同样是 append-only 单文件，1,664 行。
3. `game/data/evidence/<slug>/` —— `eye_gate` 会**清空** slug 目录，两个窗口同 slug 就跑成互相删证据。

## 三、三种并行形态

### A. 只读调研窗（推荐：现在就开一个）

一个窗口只读不写：翻开罗取证、扫缺口账、体检探针、看试玩报告，产出一份「下一批待办清单」（含每条的判据与文件落点）。

- **省什么**：主线的「读场」8–12 分钟 + 缺口梳理，而且它能在主线跑替身/长跑门那 27 分钟里同时进行 —— 那段时间主线的 CPU 是满的，但另一窗口只读文件不占 CPU。
- **风险**：几乎没有写冲突（只写一份新的 `docs/` 文件）。
- **代价**：一个窗口的启动读场（约 3–5 万 token）。
- **适合谁**：现在这个阶段 —— 缺口账里有 100 个 P 编号，梳理本身就是一件可以完全离线做的事。

### B. 双写窗口（文件集天然不相交时才开）

用 `git worktree add ../laoyoufen-b` 开第二个工作树，两条分支各做一批，只在**两边都不碰 `panels.ts` / `main.ts` / `ACCEPTANCE.md` / `ledger.md`** 时成立。

能凑出的不相交切法（从现有缺口里找）：

| 窗口 | 做什么 | 碰的文件 | 另一窗口同时做什么（不碰这些） |
| --- | --- | --- | --- |
| 写窗 1 | 纯模拟层：P510（对冲与趁势撞同一条行情时「挡坏优先」没测试钉住）、P517（`daysLeftOf` 的 O(n²)）、P499–P503 里的数值类 | `sim/invest.ts`、`sim/market.ts` + 测试 | — |
| 写窗 2 | 纯文案/手册：P511（四类门路各给一行小标题）之外的**手册页**、`data/**` 里的 `why` 与 `kairo` 校正 | `data/manual.ts`、`data/invest.ts` | 上面两窗都不碰 `panels.ts`，但**都要改 `data/invest.ts`** → 这条切法其实不成立 |

坦白说：**这个仓库现在凑不出干净的双写切法**。原因是每批的八件交付物（测试 / 探针 / 五门 / 四种子 / 文档 / ACCEPTANCE / 账本 / 部署）里，后五件是全局单例，前两件又总落在同一批热文件上。

### C. 全面并行（3 个以上写窗）

不建议。除了上面的冲突，还有两个硬约束：

- **CPU**：替身四种子是单核拉满 576 秒，长跑门要 5 分钟稳定 30 fps 以上。两个窗口同时跑门，两边都会假红（BD′ 已经踩过：并行跑出 `fps_min 29.0`，单独跑就是 56.0，后来写进了 AGENTS.md）。
- **部署**：`deploy-cli.ps1` 同时只能有一个 job 在跑（会撞远端 `/tmp/sb/NNN.b64`）。

## 四、推荐

**开一个只读调研窗，写窗口继续只有一个。**

具体这么切：

1. **主窗（写）**：按批次继续推进，下一批从 P514 开始（历史月份的门路格是假的，带 bug 性质，最该先修）。
2. **调研窗（只读）**：把 `docs/ACCEPTANCE.md` 第五节那 100 个 P 编号过一遍，按「带 bug 性质 / 玩家看得见但说不清 / 纯内部」三档分类，每条给出：判据、落点文件、能不能和别的批次并行。产出一份 `docs/待办梳理-2026-11-27.md`。
3. **两窗唯一的交汇点**：调研窗的输出只写新文件，主窗不改它 —— 零冲突。

等调研窗把缺口理清、发现某两批确实文件集不相交（比如一批纯 `sim/*` + 一批纯 `data/*`），再考虑 `git worktree` 开第二个写窗。

## 五、如果要真并行，先补三件工程债

这三件是并行的**前置条件**，也是现有的真实缺口（记为 P518–P520）：

1. **P518** `panels.ts` 2,159 行、`mountPanels` 一个函数 1,361 行 —— 每一批的界面落点都挤在同一函数里，这是并行最大的物理障碍。解法定：按页签拆成 `ui/panels/shop.ts` / `staff.ts` / `recipe.ts` / `ledger.ts`，`mountPanels` 只留装配。
   - 判据：`panels.ts` 降到 400 行以下，每个页签文件 < 500 行；`be_probe` / `bc_probe` / `bd_probe` 三条全绿不动。
   - 为什么现在不做：这是一次纯重构，八件交付物里的「四种子逐位不变」好办，但「探针全绿」要重跑 81 个探针，单独占一批都不够。
2. **P519** 账本与 ACCEPTANCE 是 append-only 单文件 —— 两个窗口各插一行就错位。解法定：账本改成 `.junshi/batches/<行号>-<slug>.md` 一批一文件，`ACCEPTANCE.md` 第一节自动从这些文件生成。
   - 判据：新增一批只 `write` 一个新文件，`ACCEPTANCE.md` 由脚本重生成，diff 只有「新增一行」。
3. **P520** 81 个探针里 41 个仍写死 `127.0.0.1` / 端口散布 27 个（4217–4246）—— 两个窗口各自的 preview 会撞端口或读错实例。解法定：全部改读 `PW_URL`，端口按 slug 哈希分配。
   - 判据：`grep 127.0.0.1 tools/gate/*_probe.py` 零命中；`PW_URL` 指向不存在的端口时探针明确报「连不上」而不是静默红。

## 六、复现

# 文件热度：最近 12 个 commit 各文件被改次数
$c = git log --format=%h -12
$all = @{}; foreach($x in $c){ git show --name-only --format="" $x | Where-Object { $_ -match '\.ts$' -and $_ -notmatch 'evidence' } | ForEach-Object { if(-not $all.ContainsKey($_)){ $all[$_] = 0 }; $all[$_]++ } }
$all.GetEnumerator() | Sort-Object Value -Descending | Select-Object -First 16

# 热文件体量
(Get-Content game/src/ui/panels.ts | Measure-Object -Line).Lines
(Get-Content game/src/ui/hud.css   | Measure-Object -Line).Lines

# 探针端口分布
Select-String -Path tools/gate/*_probe.py -Pattern 'localhost:(\d+)' -AllMatches | ForEach-Object { $_.Matches } | ForEach-Object { $_.Groups[1].Value } | Group-Object | Sort-Object Count -Descending

# 还写死 127.0.0.1 的探针
Select-String -Path tools/gate/*_probe.py -Pattern '127.0.0.1' | Select-Object -ExpandProperty Path -Unique
