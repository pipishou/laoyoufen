## 一、开罗怎么做的（对着取证翻的，有出处）

翻 `D:\项目\REA\REA\逆向\_逆向上游\TheRamenSensei\取证\`，得到四条可直接对照的事实：

1. **三档 dpi 各出一套贴图，让系统按 dpi 挑资源，而不是运行时缩一张图。**
   `textassets\system_out\` 里同一张虚拟键盘贴图三份并存：
   `drawable-ldpi__keypad01.png` **384×192** / `drawable-mdpi__keypad01.png` **512×256** / `drawable-hdpi__keypad01.png` **768×384**。
   （`battery.png`、`buttoneffect.png`、`keypad02.png` 同样三档。）倍率 1 : 1.333 : 2。
2. **有专门的触摸反馈贴图。** `drawable-{l,m,h}dpi__touch_effect.png` = **60×24**，三档尺寸相同（它是个效果，不是控件）。
3. **横屏是构建期常量，不是运行时猜的。** `取证\dump\dump.cs:18839 public static bool LANDSCAPE_GAME; // 0x3D`、`:18848 public static bool SCREEN_ROTATION; // 0x49`（都在 `public class Config // TypeDefIndex: 551` 里），配合 `:39294 public abstract class IApplication` 的 `:39302 private ScreenOrientation defaultOrientation_`、`:19679 public class DisplayMetrics`（`WidthPixels`/`HeightPixels`/`Density`/`DensityDPI` 全是 `static` 属性）。
4. **整套美术库是横屏布局的。** `textassets` 下 **1877 张 png**，其中「高 > 宽 且 高 ≥ 200」的竖图只有 **8 张**；最宽的第 3 名是 `com_out\side_view_pad_480.png` **768×480**。

**对照结论**：开罗不是「一套 1024×768 硬缩」，它是**按 dpi 换资源 + 声明式横屏**，所以它的按钮在每台手机上物理尺寸都差不多。
本作是「一套 1024×768 舞台 + CSS `transform: scale()`」，缩放在 CSS 层做 —— 这个选择本身没错（`world.ts:642-672` 的注释写清了为什么用 `Phaser.Scale.NONE`：缩放交给 CSS，否则 canvas 尺寸变了会与 HUD 脱层），
但它有一个副作用：**凡是写在 CSS 里的像素数，都被一起缩了。**

三个写法不是随手写的（子窗 `pwa-recon` 的结论，逐条都验过）：

| 写法 | 为什么 | 写成别的会怎样 |
| --- | --- | --- |

| `display: "fullscreen"` | Android 零 chrome；iOS **不实现** `fullscreen`，按回退链自动落 `standalone`（同样零地址栏） | 一份值满足两端，不需要 `display_override` |

### 2.4 `game/src/ui/viewport.ts`（74 → 162 行）

```ts
export function fitScale(vw: number, vh: number, padX = 0, padY = 0): number {
  const availW = Math.max(1, vw - padX);
  const availH = Math.max(1, vh - padY);
  const raw = Math.min(availW / STAGE_W, availH / STAGE_H);
  return Math.max(0.2, Math.min(raw, 3));
}
```

为什么必须扣 `body` 的 padding：`viewportSize()` 读的是 `window.visualViewport`，它**不含 body padding**。安全区一补上（横屏刘海机 `left/right` 实测 44–59px），`#stage` 就会被 `overflow: hidden` 裁掉左右边。所以算式抽成纯函数、把 padding 当参数传，才测得出这件事（`viewport.test.ts` 7 条）。

另加 `enterFullscreenLandscape()`：用户在**手势内**先 `requestFullscreen()` 成功，再 `screen.orientation.lock("landscape")`，两步各自 `try/catch` 静默回退。
（顺序不能反：`lock()` 要求「已在全屏上下文」；iPhone 不支持元素级 Fullscreen API，`requestFullscreen()` 直接抛 TypeError ⇒ 走 catch，什么都不发生，页面照旧可玩。）

### 3.2 试过并否掉的两个方案（教训，别再试）

1. **伪元素扩大命中区。** `#hud button::after { width: max(100%, var(--tap-min)) }` —— 两个问题：
   ① 会**盖住相邻按钮**（点「设置」触发「音乐」）；
   ② `getBoundingClientRect()` **量不到伪元素** ⇒ 探针测不出假绿，最坏的一种错。
2. **旋转舞台。** `#stage { transform: rotate(-90deg) scale(s) }`，`s` 按 `min(w/768, h/1024)` 算。
   实测 `360×640 → scale 0.4688 舞台 270×360`、`375×667 → 0.4883 舞台 281×375`，**占屏仍是 42%** —— 旋转不增加像素面积，只换方向，反而让玩家要歪着头。

**「占屏 42%」是几何必然**：4:3 的舞台塞进 9:16 的屏幕，剩下 58% 只能是黑边。这条不靠改 CSS 解决，靠「劝横屏 + 横屏能玩」解决。

- **线上与本地逐字节相同（SHA256）**：
  `manifest.json` `4A6DB040…D81531AD`（997 B）、`icons/icon-512.png` `A8BEEB47…CB2DEB449`（2041 B）、`assets/index-BSSaDzih.js` `C8604F9E…3CBCDEF20`（1,767,007 B）。
- **判别力验证**（这条新断言不是恒绿的）：`/laoyoufen.prev/manifest.json` 与 `/laoyoufen.prev/icons/icon-512.png` 都 **404** ⇒ 没部署时一定红。

### 线上仍然装不成 PWA 的一件事（不是 bug，是明文 HTTP 的硬限制）

线上是 `http://8.134.86.249`，**明文 HTTP ⇒ Android 上不会出现「安装应用」入口**（只有「添加到主屏幕」这个快捷方式，`display` / `orientation` 都不生效）。iOS 不受影响（走 `apple-mobile-web-app-*` 那套）。

要真变成可安装 PWA 得给这个 IP 配证书 —— 但现有的 Let's Encrypt 证书 `subject=CN=8-134-86-249.sslip.io`，**SAN 只有 `DNS:8-134-86-249.sslip.io`，没有 IP**，用 `https://8.134.86.249` 访问会证书告警。所以这件事记成 **P556**，不在本批动。

## 五、新缺口

**P555 顶栏 / 底栏六类小按钮的真实热区只有 10–16 屏幕像素。**
`spd` 13×10、`chip` 16×12、`prefsbtn` 15×16、`audio` 15×16、`pill` 29×16、`btn`（配方）34×29。
**为什么本批不做**：顶栏高 52、底栏高 100（舞台坐标），塞不下「44 / 0.366 ≈ 120」舞台像素的按钮。伪元素与旋转两条捷径都试过并否掉（见 3.2）。
**判据**：375×667 竖屏下这六类的 `getBoundingClientRect().height` 全部 ≥ 44。**要做的事**：一套专门的手机版 HUD（顶栏改成两行或收进抽屉、底栏改图标 + 更大间距），这是新布局，不是调数值。

**P556 线上明文 HTTP ⇒ Android 装不成 PWA；且现有证书没有 IP SAN。**
**判据**：`https://8.134.86.249/laoyoufen/` 无证书告警且 Chrome 出现「安装应用」。**要做的事**：给这个 IP 申一张带 IP SAN 的证书（或把站点挪到一个真域名下），再验一遍 manifest 的 `display`/`orientation` 是否生效。

**P557 竖屏没有独立布局，只有「点我横屏」一个出口。**
舞台占屏 42% 是几何必然（4:3 塞 9:16），本批的答案是「劝横屏 + 横屏能玩」。但玩家如果就是不横屏，他看到的是一个 270px 高的小窗 + 底部一颗按钮。
**判据**：竖屏 360×640 下，舞台占屏 ≥ 70%（需要一套纵向重排的 HUD，比如顶栏/底栏变成侧边抽屉，舞台只留灶台与客人）。
**为什么现在不做**：那是新布局 + 新美术，与本批「让现有横屏形态在手机上成立」是两件事。
