# 试玩二轮修复 第 4 批：F7–F12

> 2026-11-19 · 对应 `docs/试玩二轮评估与优化方案-2026-11-19.md` 第七节的第 4 批
> 六项改动里三项真改了代码、两项被数据否决只留说明、一项只动 CSS。

## 一、三句话

1. **家当的产能件以前不标红**，玩家在流失 60% 的那几天看不出该买家当；现在六件效率件（洗碗池/大砧板/冰柜/壁扇/抽油烟机/排风扇）会跟着「现在最缺」一起标红，并打「省事」小标。
2. **热卖槽与时段客流这两项，改参数会让游戏更差** —— 两组替身实验都记录在案：热卖参数一调，热卖次数从 74 次掉到 12 次；按时段改人群构成，流失从 68% 顶到 77%。所以这两项只改说明、把表写进代码但开关默认关，等「分时段定价」这种配套出现再打开。
3. **引导卡不再压面板**：宽屏挪到右上角，窄屏压成 stage 顶部一条横条。窄屏之所以难，是因为 stage 固定 1024×768 缩到 390 宽只剩约 290px 高。

## 二、F7 家当产能件红标

`game/src/sim/gear.ts`：

```ts
export const GEAR_EFFICIENCY_IDS: ReadonlySet<string> = new Set<GearId>([
  "wash_sink", "big_board", "freezer", "wall_fan", "hood", "aroma_fan",
]);

/** 还没买的效率件，按价格升序 —— 面板与钩子都用这一份。 */
export function gearEfficiencyLeft(state: GameState): GearDef[] {
  const owned = new Set(state.gear ?? []);
  return GEARS.filter((g) => GEAR_EFFICIENCY_IDS.has(g.id) && !owned.has(g.id))
    .sort((a, b) => a.costYuan - b.costYuan);
}
```

`game/src/ui/panels.ts`：

```ts
const gearHot = lostRateOf(s) >= CAPACITY_LOST_RATE && gearEfficiencyLeft(s).length > 0;
// 家当段标题
`<div class="sechd${gearHot ? " hot" : ""}">${icon("crate")}家当 · ${gearSummary(s)}</div>`
// 未买的效率件行
`<span class="tag2 hot2">省事</span>`
```

CSS 只加一行：`.tag2.hot2{border-color:var(--red);color:var(--red)}`。

**为什么只标这六件**：锦旗（抢客）与祖师像（进店+满意）不是「接客能力」，标成省事会误导；三件设备（灶/粉篓/案台）自己那一段已经有红标。

## 三、F8 设备 toast 说真话

以前三件设备无论升哪一档，toast 都是同一句「设备换了，明天出碗更快」——粉篓升档其实是省料钱，不是出碗快。

```ts
function upgradeLine(id: EquipId, level: number): string {
  if (id === "stove") { const pct = Math.round((1 - STOVE_SERVE_FACTOR) * 100); return `猛火灶第 ${level} 档：出碗时间每档 −${pct}%`; }
  if (id === "strainer") { const pct = Math.round((1 - STRAINER_COST_FACTOR) * 100); return `粉篓第 ${level} 档：料钱每档 −${pct}%`; }
  return `案台第 ${level} 档：每天多备 ${BENCH_CAPACITY_STEP} 碗的料`;
}
```

数值从常量算，不写死（改平衡时文案自动跟着走）。`main.ts` 的 `buyEquip` 改成 `r.line ?? "设备换了，明天出碗更快"`。

## 四、F9 时段偏置：表写了，开关默认关

报告说「考生下午来、夜宵党夜里来」不成立。我做了 `DAYPART_BIAS`（四个时段 × 十几个原型）并接进 `pickArchetype`，然后跑替身对照：

| 方案 | 种子 1 月均 | 种子 2 月均 | 流失 |
|---|---|---|---|
| D 批基线 | ¥74,649 | ¥79,539 | 68% / 69% |
| 温和偏置（1.1–1.5 倍） | ¥51,106 | ¥49,612 | **77%** |
| 偏置空表（= 基线） | ¥45,667 | ¥46,626 | — |

**结论**：单一定价的店一旦按时段放大低预算原型，买不起就走，流失从 68% 顶到 77%，月均掉三成。这不是「时段化不好」，是**时段化必须配分时段定价/分时段款**，否则只是把高峰做尖。

所以代码里保留 `DAYPART_BIAS` 与 `DAYPART_BIAS_ENABLED = false`，注释写明原因。行为上等于基线 —— 用 `probe:standin` 复核：种子 1 ¥74,649、种子 2 ¥79,539，与 D 批逐位一致。

## 五、F10 热卖槽：只改说明，不调参

报告说 2 座店热卖几乎不动。我先试了「让它更容易满」（`PER_BOWL 2→3`、`MAX_GAIN 8→12`、`DECAY 2→1`）：

| 方案 | 种子 1 热卖次数 | 种子 2 热卖次数 |
|---|---|---|
| 基线 | 74 | 34 |
| 参数放宽 | **12** | 153 |

**为什么反而更少**：槽越早满，就越早进「30 分钟热卖 + 240 分钟冷却」的冻结期；一天总共 8 小时营业，早满一次就再没有第二次。放宽参数只是把唯一那一次往前挪。

所以只改 HUD 的说明文字：

> 热卖：门口有人排队、客人又吃得满意，槽就往上走；出碗越慢的店攒得越吃力。涨满后来客翻倍半小时

「出碗越慢越吃力」直接告诉玩家这是产能的函数，不是玄学。

## 六、F11 段位差客折算天数

`applyGrade` 失败时以前只说「还差 120 位客人」。现在读最后一天的营业量折算：

```ts
const lastDay = s.days[s.days.length - 1];
const perDay = lastDay && lastDay.served > 0 ? lastDay.served : 0;
// 有值 → 「还差 120 位客人（按昨天卖了 40 碗算，约 3 天）」
```

没有营业记录就不编天数（宁可少说，不说错）。

## 七、F12 引导卡不挡面板

**宽屏**：`.guide` 从「底部居中 460px 宽」改成「右上角 300px 宽、max-height 52%」——原来它正好压在汤底滑条与评分卡上。

**窄屏的真正难点**：`#stage` 固定 `1024×768` 再按 `--stage-scale` 缩放（`hud.responsive.css`），390×844 的视口里 stage 只剩约 **290px 高**。任何竖着放的卡片都会撞到右下角的评分卡（屏幕 y=331）。

试过两版都不行（`top:96px + max-height:26%` → 底边 360 撞 331），最后改成**顶部横条**：

```css
@media (max-width:520px){
  .guide{ left:4px; right:4px; top:4px; bottom:auto; width:auto;
          max-height:70px; padding:5px 7px 4px; overflow:auto;
          font-size:11px; line-height:1.45; }
  .guide .gtitle{font-size:12.5px}
  .guide .gfoot{margin-top:3px;padding-top:3px}
  .guide .gbtn{min-height:22px;padding:2px 8px;font-size:11px}
}
```

实测窄屏：guide `y=254, h=27`（屏幕坐标），滑条 `y=356`、评分卡 `y=331` —— 不相交。

## 九、缺口

- **P92** 热卖的「早满即冻结」是个反直觉的机制，玩家永远学不到；要么改成可叠加多次，要么在 HUD 上直接写「今天已经热卖过」。
- **P93** 时段偏置表存在但没有配套的分时段定价，玩家开不了；等「早市/夜市两套价」再做。
- **P94** 窄屏引导条只有 27px 高（屏幕），正文要滚；更好的做法是窄屏默认只显示标题 + 一个「展开」。
